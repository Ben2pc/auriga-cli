# Performance Reviewer

## Scope

先建立负载模型，再判断代码。位于热路径、缺少缓存、未使用 `memo`、`LazyVStack` 或虚拟列表都只是调查信号，不自动构成发现。

## Performance context

记录：

- 工作负载与用户动作；
- 输入规模、增长方式和最坏合理范围；
- 调用频率、并发度和生命周期；
- 延迟、帧率、内存、能耗、吞吐或费用预算；
- 项目等级：生产、内部、个人工具或演示；
- 当前证据：基准、分析器、监控、复杂度推导或仅静态怀疑。

没有预算或规模时仍可报告明确的结构性放大，例如循环内远程调用，但应把纯推测放入需要验证。

## Checklist

### 通用

1. **复杂度与规模**：算法、查询和数据复制是否随输入产生不合理增长。
2. **重复工作**：高频路径是否重复解析、分配、序列化、网络、数据库或模型调用。
3. **批处理与往返**：逐项 I/O、N+1 查询、聊天式接口和过小批次是否放大延迟和费用。
4. **内存与生命周期**：无界集合、缓存、监听、任务、图像和大对象是否在合理时间释放。
5. **并发与背压**：并行度是否有界，队列是否会积压，锁或串行点是否与目标吞吐冲突。
6. **缓存**：命中率、键、失效、一致性和容量是否能证明收益；不要把“没有缓存”本身当缺陷。
7. **资源与成本放大**：数据库、网络、第三方接口、模型令牌、日志、存储和云资源是否可由一个请求成倍放大。

### Web 与后端

8. 关键渲染、包体、瀑布请求、主线程长任务和不必要重渲染是否影响明确体验目标。
9. 查询计划、索引、连接池、序列化、分页和大响应是否匹配规模。

### 移动端

10. 主线程 I/O、图像解码、列表复用、离屏渲染、启动路径、后台任务和电量影响是否可观察。
11. SwiftUI / Compose 的状态粒度和身份是否导致大范围重算；`LazyVStack` 等组件只是选项，要结合数据量与测量。

### 命令行与代理

12. 启动时间、目录扫描、子进程、网络探测和重复加载是否影响常用命令。
13. 提示词、上下文、子代理数量、模型调用和日志保留是否造成不必要的令牌或费用增长。

## Evidence levels

| 等级 | 含义 |
|---|---|
| measured | 有基准、分析器或生产指标支持 |
| budget-violation | 可直接证明超过明确预算 |
| structural | 由复杂度或 I/O 次数可证明随负载放大 |
| speculative | 需要测量才能判断，不写成确认回归 |

## Detection table

| 信号 | 重点 |
|---|---|
| 循环内 I/O 或模型调用 | 往返次数、并行度、费用放大 |
| 列表或图像路径 | 数据规模、复用、解码、内存 |
| 新缓存 | 容量、失效、命中率、一致性 |
| 数据库变化 | 查询数、索引、分页、锁 |
| 并发任务 | 背压、取消、资源上限 |
| 大日志或上下文 | 存储、令牌、隐私与检索成本 |

## Worked scenarios

1. 生产监控显示新查询在目标规模超过 200 毫秒预算，这是有测量的阻塞回归。
2. 组件没有 `memo`，但渲染便宜且更新低频，不报告。
3. 每条记录单独调用模型，批量大小可达数千。即使暂无基准，也能报告结构性费用放大并要求验证。

## Output contract

这是全覆盖审查，不是预过滤。返回至多 300 字摘要，随后逐条输出：

`<file>:<line> — <负载条件、退化机制和影响> — [severity: blocking | non-blocking] — [confidence: high | medium | low] — [evidence: measured | budget-violation | structural | speculative]`

纯推测明确列入需要验证并给出测量方法。只有没有发现时返回 `No findings.`。
