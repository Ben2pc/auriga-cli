# 拉取请求流程

按当前操作读取对应章节；授权与工作树保护遵循 `git-workflow` 入口。

## 创建或更新草稿请求

首个有意义的提交验证并推送后，尽早创建 Draft 拉取请求。正文使用中文二级标题，保留摘要、验收标准和验证计划；设计决策、风险和后续事项仅有实质内容时展开，不用“无”填充空节。

验收标准表示当前拉取请求必须成立的可验证结果，可以来自正式规格或用户的口头要求，不限定为产品需求。验收与验证中的合并前事项使用勾选清单；实际完成后勾选，验证依据有效证据。设计取舍只记录真实决定，不编造候选。

```markdown
## 摘要

本次变更解决了什么问题，以及为什么现在需要处理。

## 验收标准

- [ ] 用户或调用方能够观察到的结果成立。
- [ ] 既有行为与兼容性约束得到保留。

## 验证计划

- [ ] <本次适用的验证与通过标准；完成后记录实际结果和证据>。
```

有内容时添加“设计决策”“风险”“后续事项”二级章节，分别写明必要取舍、影响与限制、延期事项及原因；后续事项使用普通条目。

创建或更新后读取远端拉取请求的标题与正文，确认标题符合 Conventional Commits，正文与当前提交一致；发现漂移就直接更新。

## 进入待评审状态

进入 Ready 前确认：

- 所有当前提交已推送，基准分支与目标分支正确。
- 最后一次相关修改后，本次适用的验证方式与项目必需检查已完成；纯说明改动不为凑齐类别额外构建或手工验证。
- 正文反映最终范围、验收、决定、风险、验证证据和真实后续事项；验证摘要依据 `validation-results.md` 的有效证据，无文件时依据实际执行结果。
- 当前拉取请求的临时规格与计划已按用户选择晋升、归档或删除；`validation-results.md` 按 `spec-design` 的结果生命周期处理，保留可追溯证据；该动作用 `documentation-management` 执行，不直接移动文件。跨拉取请求的长期规范保持原位。

收尾直接汇报验证结果与缺口，并链接可用记录；不能只给链接。

Hook 会检查可确定的结构问题和未推送提交，但不能替代以上判断。

## 处理评审与持续集成反馈

- 逐项判断为修复、延期或不处理，并保留理由；不要因为评审出现就自动扩大范围。
- 一批处理完成后向用户汇总问题、状态和对应提交；已明确授权对外回复时，再在拉取请求会话中汇总或单独澄清。
- 不擅自关闭仍需评审者确认的讨论。
- 新发现改变了范围、设计决定、风险或后续事项时，同步更新正文；批次评论不代替提交信息中的理由。

## 合并

- 确认用户已授权合并，拉取请求仍指向预期提交，必需检查与批准均满足。
- 验收标准和验证计划中的合并前事项必须完成；无法在合并前完成的真实后续工作移到“后续事项”，写成普通条目并说明原因。
- 读取仓库允许且惯用的合并策略，不默认选择压缩、变基或合并提交。
- 合并后确认远端状态和合并提交，再清理已经不需要的本地与远端任务分支。
