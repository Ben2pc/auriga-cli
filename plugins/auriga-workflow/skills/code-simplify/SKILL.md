# 代码简化

简化代码、识别坏味道、降低维护成本。范围是函数、类、文件**内部**,以及它们之间局部的搬移——不下沉的另一头是 `arch-design`(模块、依赖、分层那个高度)。

**为什么需要它**:代码有一份隐形成本——每一次未来的改动,都要先读懂它。读不懂、绕来绕去、到处重复,这份成本就高,而且复利累积。坏味道不是道德问题,是赶工迭代留下的残渣。简化的目的是给"未来每一次改动"减成本,不是把行数压少。判断一次简化成不成功只有一个标准:**一个新来的同事,读简化后的版本,是不是比读原来的更快搞懂。**

它同时反对两件事:**不敢碰**(代码烂下去,因为没人敢动)和**过度简化**(把代码压成需要停下来想一下才能解析的"聪明"写法,或顺手重构无关代码、撑大 diff)。贯穿全文的一条红线:**简化严格保留对外可见行为**——只改代码怎么表达,不改它做什么。

## 两种唤起方式与确认闸门

这个 skill 有两条入口,处理方式不同——区别只在"用户有没有开口要"。

**用户主动调用 / 明确要求简化** → 直接按下面的流程做。用户已经授权了。

**Agent 主动发现并唤起**(你在读代码、或改别的东西时,撞见明显影响可维护性的坏味道)→ **先确认,再动手。不要直接改。** 先给用户一份简短报告:

- 发现了什么坏味道,在哪个文件、哪一段;
- 它的维护成本——这段代码改得勤不勤、出过 bug 没、读它的人多不多;
- 建议怎么改、用什么手法;
- 影响范围——会动几个文件、几处调用、几套测试。

等用户点头(或挑其中几项),才进入流程。**为什么要这道闸门**:用户没要求时擅自改代码,会制造他没预期的 diff、打断他正在做的事、把一个"清理"混进一个"修 bug"的提交里。主动发现问题是有价值的——但发现 ≠ 动手。报告并等确认,把决定权交还用户。

## 几条铁律

**一、严格保留对外可见行为。** 所有输入、输出、副作用、错误行为、边界情况,简化前后必须完全一致。拿不准某次简化会不会动到行为,就不做。一个直接的检验:如果简化逼着你改测试才能通过,你多半已经改了行为——退回去。

**二、先理解,再动手(Chesterton 栅栏)。** 看到一段绕的代码,先搞清它为什么这么写,再决定要不要改——可能是性能、平台限制、历史原因。看不懂就先读够上下文、查 git blame。回答不了"它为什么在这儿",就还没准备好简化它。

**三、跟随项目约定。** 简化是让代码更贴合代码库里既有的模式,不是把个人偏好塞进去。先读 CLAUDE.md / AGENTS.md、看邻近代码怎么处理同类情况——导入顺序、命名、错误处理、类型标注深度。破坏一致性的"简化"不是简化,是制造噪声。

**四、只动相关范围。** 默认只简化手头正在碰的代码。不要顺手重构无关代码——那会让 diff 变脏、给没打算改的地方引入回归风险。要扩大范围,明说,或走扫描模式。

**五、小步走,每步验证。** 一次一个手法,改完跑测试,绿了再下一个。不要把一堆简化攒成一个没测过的大改动——出问题你会不知道是哪一步。**简化提交和功能 / bug 修复提交分开**:一个 PR 里既重构又加功能,是两个 PR。

**六、清晰胜于聪明。** 显式的代码胜过紧凑的代码——只要紧凑的那版需要停下来想一下才能读懂。行数少不是目标,读得快才是。

## 什么时候用

- 功能写完、测试过了,但实现比它该有的样子重。
- 代码审查时,可读性或复杂度被点出来。
- 撞见深层嵌套、超长函数、含糊命名。
- 赶工期写下的代码,事后回来收拾。
- 合并后引入了重复或不一致。
- 对一个目录 / 模块做定期的坏味道普查(扫描模式)。

**不要用于:**

- **代码已经清楚**——别为简化而简化。
- **还没搞懂这段代码做什么**——先理解(铁律二)。
- **性能关键,而"更简单"的版本会实测更慢。**
- **马上要整个重写这个模块**——简化将被丢弃的代码是白费力。
- **改动会改变对外可见行为**——那是新功能或 bug 修复,不是简化;走 `spec-design` 或 `systematic-debugging`。
- **问题在模块结构、依赖方向、分层这个高度**——那归 `arch-design`。一句话分界:动的是模块**边界** → `arch-design`;动的是模块**内部** → 这个 skill。

## 流程

```
A. 框定        →  B. 理解        →  C. 识别坏味道        →  D. 小步执行        →  E. 验收
   (范围与模式)     (Chesterton)      (查目录、定手法)        (一次一个、每步跑测试)     (整体回看)
```

### A 框定范围与模式

- Agent 主动唤起的,**先过确认闸门**(见上)。
- 定清楚要动的范围:是手头某个文件 / 函数的单点清理,还是对一个目录 / 模块的普查(扫描模式,见下文)。
- 单点清理:范围就是你正在碰的那段代码,不外扩。

### B 理解(Chesterton 栅栏)

动任何代码之前,回答得出:

- 这段代码的职责是什么?谁调用它?它调用谁?
- 边界情况和错误路径有哪些?
- 有没有测试定义了它的预期行为?
- 它**为什么**写成这样?(性能?平台约束?历史原因?)查 git blame。

回答不了,就先读上下文,别动。

### C 识别坏味道

扫描代码,认出**具体的坏味道**——每一种都是一个明确的信号,不是模糊的"我觉得乱"。下文「快速识别表」列了最常撞见的那几种,够你一眼认出。**完整的坏味道目录(对齐《重构》的二十多种)和对应的重构手法,见 `references/smells-and-refactorings.md`**——识别到不在快速表里的坏味道、或拿不准该用什么手法时,读它。

### D 小步执行

对每一个要做的简化:

1. 做这一个改动(一个手法)。
2. 跑测试套件。
3. 绿了 → 提交,或继续下一个。
4. 红了 → 退回,重新想。

大手法(提炼类、以多态取代条件这类**改形状**的)本身就是一串小手法的有纪律序列——拆成小步做,每步之间系统都保持可编译、可测试。手法目录见 `references/smells-and-refactorings.md`。

**500 行规则**:如果一次简化要动 500 行以上,投资自动化(codemod、脚本、AST 变换),别手改——那个规模手改既易错又难审。

各语言的简化前后示例见 `references/language-examples.md`。

### E 验收

全部做完,退一步看整体——过下文「验收清单」。如果"简化后"的版本反而更难读、更难审,**退回**。不是每次简化尝试都会成功。

### 扫描模式(目录 / 模块普查)

当任务是"扫描并优化一块代码库",而不是单点清理:

1. 划定扫描范围(一个目录、一个模块)。
2. 逐文件过坏味道目录,记录:坏味道类型、位置、维护成本信号(改动频率、bug 历史、被多少处依赖)。
3. 产出一份**按维护成本排序**的清单——高成本的排前面。**不要直接改。**
4. 把清单交给用户,**用户挑哪些动**。
5. 对选中的项,逐个走 B→D。

扫描模式天然带确认闸门——产出清单、等用户挑,本身就是确认。

## 快速识别表

最常撞见的坏味道,够一眼认出。完整目录见 `references/smells-and-refactorings.md`。

**结构复杂度**

| 坏味道 | 信号 | 简化方向 |
|---|---|---|
| 深层嵌套(3+ 层) | 控制流难追 | 抽出守卫子句,或提炼成有名字的辅助函数 |
| 超长函数(50+ 行) | 多个职责挤在一起 | 拆成职责单一、命名清楚的小函数 |
| 嵌套三元 | 要在脑子里压栈才能解析 | 换成 if/else 链、switch 或查找表 |
| 布尔参数标志 | `doThing(true, false)` 看不出意思 | 换成选项对象,或拆成多个函数 |
| 重复的条件判断 | 同一个 if 散在多处 | 提炼成一个命名清楚的判定函数 |

**命名与可读性**

| 坏味道 | 信号 | 简化方向 |
|---|---|---|
| 泛化命名 | `data` `result` `tmp` `val` 不说明内容 | 改成描述内容的名字 |
| 缩写命名 | `usr` `cfg` `btn` 要猜 | 用完整词,除非是通用缩写(`id`、`url`) |
| 误导性命名 | 名叫 `get` 却改了状态 | 改成反映真实行为的名字 |
| 解释"做什么"的注释 | `// 计数器加一` 和代码重复 | 删注释——代码本身够清楚 |
| 解释"为什么"的注释 | 携带代码表达不出的意图 | **留着** |

**冗余**

| 坏味道 | 信号 | 简化方向 |
|---|---|---|
| 重复代码 | 同样 5+ 行散在多处 | 提炼成共享函数 |
| 死代码 | 不可达分支、未用变量、注释掉的块 | 删(确认真死之后) |
| 没价值的包装 | 包了一层却没替调用方省事 | 内联,直接调底层 |
| 过度设计 | 工厂的工厂、只有一种策略的策略模式 | 换成直接的简单写法 |
| 推测性通用化 | 为想象中的需求留的抽象 | 删,等真需要再加 |

## 维护成本视角:值不值得简化

不是所有坏味道都值得动。判断优先级看三个信号:

- **改动频率**——这段代码最近改得勤吗?(`git log`)高频改的地方,每次都付难懂的成本。
- **bug 历史**——这里出过几次 bug?反复出 bug 常常是坏味道在作祟。
- **读者数量**——多少处依赖它?读者越多,难懂的成本乘数越大。

高频改 + 难懂 + 出过 bug = 优先简化。几乎不动、没人读的角落 = 别碰——简化它不产生回报,还白担回归风险。这就是"降低维护成本"落到可操作:把力气花在成本真正高的地方。

## 常见自我辩解

| 自我辩解 | 实情 |
|---|---|
| "能跑就别碰" | 能跑但难读的代码,坏的时候也难修。现在简化,省的是未来每次改动的时间。 |
| "行数越少越简单" | 一行嵌套三元不比五行 if/else 简单。简单是理解速度,不是行数。 |
| "顺手把旁边那段也简化了" | 无关简化让 diff 变脏,给没打算改的地方引入回归。守住范围。 |
| "类型已经自文档了" | 类型说明结构,不说明意图。命名清楚的函数比类型签名更能解释"为什么"。 |
| "这个抽象以后可能有用" | 别留推测性抽象。现在没用,就是没价值的复杂度。删掉,真要用再加。 |
| "原作者肯定有理由" | 也许。查 git blame,用 Chesterton 栅栏。但累积的复杂度往往没理由,只是赶工的残渣。 |
| "我加功能时顺便重构了" | 重构和功能分开。混在一起的改动难审、难回退、难在历史里看懂。 |

## 红旗

- 简化逼着你改测试才能过——你多半改了行为。
- "简化后"的代码比原来更长、更难追。
- 按个人偏好改名,而不是按项目约定。
- 为了"代码更干净"删掉错误处理。
- 简化你没完全搞懂的代码。
- 一堆简化攒成一个大的、难审的提交。
- 没被要求就重构当前任务范围外的代码。

## 验收清单

- [ ] 所有既有测试不改就通过。
- [ ] 构建成功,没有新警告;检查器 / 格式化器通过。
- [ ] 每个简化是一个可独立审查的增量改动;diff 干净,没混入无关改动。
- [ ] 简化后的代码跟随项目约定(对照 CLAUDE.md / AGENTS.md)。
- [ ] 没有删弱任何错误处理。
- [ ] 没留死代码(未用导入、不可达分支)。
- [ ](Agent 主动唤起时)动手前已报告并拿到用户确认。
- [ ] 一个同事或审查 agent 会认可这次改动是净改进。

## 反模式

- ❌ Agent 主动发现坏味道就直接改——必须先报告、等确认。
- ❌ 把行为变更混进简化——简化不改对外行为;行为变了就是新功能或 bug 修复。
- ❌ 为简化而简化——代码已经清楚就别动。
- ❌ 简化没搞懂的代码——先理解(Chesterton 栅栏)。
- ❌ 顺手重构无关代码——撑大 diff、引入回归。
- ❌ 一堆简化攒成一个大提交——出问题定位不到。
- ❌ 简化和功能 / bug 修复混在一个提交——难审、难回退。
- ❌ 用行数当简化的成功标准——理解速度才是。
- ❌ 简化马上要重写的代码——白费力。
- ❌ 把模块结构 / 依赖 / 分层的问题在这里处理——那是 `arch-design` 的高度。

## 和其他 skill 的关系

- `arch-design`——模块、依赖方向、分层这个高度的结构问题归它;函数、类、文件内部以及它们之间的局部清理归这个 skill。动的是模块边界 → `arch-design`;动的是模块内部 → `code-simplify`。
- `test-designer`——简化的前提是行为有测试盖住(铁律一)。保护网测试缺失、而行为面不显然时,由它设计特征测试,再开始简化。
- `systematic-debugging`——如果"坏味道"其实是个有复现步骤的 bug,那是缺陷,不是简化对象,走它。
