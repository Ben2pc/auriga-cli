# `spec.md` 模板

文件化规格触发时，将下面的模板复制到 `docs/specs/<topic>/spec.md`。跨多个 PR 的总规范只有在用户明确确认长期生命周期后，才写入 `docs/long-running-specs/<topic>/spec.md`；当前子 PR 仍维护自己的规格。

使用约定：

- 保留双语章节标题和层级编号，正文使用对话语言；删除写作提示和占位符，不适用的可选章节直接删除，不用“无”填满形式。
- 按“产品总览 → 产品需求分项”组织。总览只保存共同目标、整体体验、共享产品规则和范围；每个分项保存一组紧密相关的原始需求及其用户可感知行为。
- 优先根据原始产品需求描述或 PRD 的产品功能结构组织分项：沿用有业务意义的章节名称、层级和顺序，并在来源结构对齐表中记录对应关系；背景、修订记录、排期等非功能章节不机械复制为需求分项。
- 没有可参考的前置产物或来源结构时，按用户可感知的产品子功能划分。一个子功能应有用户能够识别的触发场景和可观察结果；不能按后端模块、接口、数据表、类或实施步骤划分产品需求。
- 跨多个分项共同成立的产品规则只在总览定义一次，分项引用；原始需求必须落入具体分项，不能只留在总览概括。
- `validation-contract.md` 使用与本文件相同的分项名称和顺序；每个分项直接列出对应 VAL，避免另建一套验收分类结构。
- 只记录确认后的价值、事实和行为，不保存逐题问答流水。
- `Open questions` 只保存有意交给架构或实施阶段的决定，并写明归属和推迟理由；未解决的产品歧义必须回到需求澄清。

```markdown
# <主题> — Spec（<主题> — 规范）

> <一句话说明要为谁解决什么问题，以及整体可观察结果。>

## 1. Product Overview / 产品总览

### 1.1 Why / 为什么做

- **问题与用户**：<谁在什么场景遇到什么问题。>
- **事实依据**：<用户反馈、使用数据、当前行为、故障或其他证据。>
- **价值与时机**：<为什么值得现在解决；预期改善什么结果。>
- **替代方案**：<为什么不选择不做、人工处理或更小方案。>

### 1.2 Source Structure Alignment / 来源结构对齐

> 按原始产品需求描述或产品需求文档中的产品功能章节顺序填写。若没有前置结构，来源写“用户需求描述”，原始章节写“无”，规格落点按用户可感知的产品子功能命名。

| 来源 | 原始章节或需求 | 规格落点 | 对齐说明 |
|---|---|---|---|
| `<产品需求文档、原型、用户描述或其他权威来源>` | `<原始章节标题、条款或需求描述>` | `2.1 <产品分项名称>` | <沿用、合并或拆分的理由；直接对应时写“直接对应”> |

### 1.3 Overall Product Experience / 整体产品体验

- **目标用户与场景**：<谁在什么整体场景使用。>
- **端到端结果**：<用户从开始到结束能观察到什么变化。>
- **共享产品规则**：<跨多个分项共同成立的产品规则；没有则删除。>
- **总体范围**：<本规格覆盖哪些产品能力。>

### 1.4 Findings / 调研发现

> 可选。只写与需求决定有关的当前事实，每项锚定代码、接口、数据、文档或外部来源。

- `<事实来源>`：<已核实事实及其对产品需求的影响>

## 2. Product Requirement Details / 产品需求分项

> 有产品需求文档时，按其中有业务意义的产品功能章节命名和排序；没有来源结构时，按用户可感知的产品子功能组织。复制 `2.1` 形成其他同级分项，并保持每项“原始需求 → 用户可感知行为 → 范围边界 → 验收映射”的结构。

### 2.1 `<产品需求文档中的功能章节，或用户可感知的产品子功能>`

#### 2.1.1 Original Product Requirement / 原始产品需求

- **来源**：`<来源文件或用户已确认描述>#<章节、条款或定位信息>`
- **原始需求**：<忠实概括该分项承接的原始产品要求；保留会改变用户结果的条件，不改写成技术方案。>

#### 2.1.2 User-visible Behavior / 用户可感知行为

- **目标用户与场景**：<谁在什么场景进入本子功能。>
- **触发与前置条件**：<用户做什么，或什么产品事件发生。>
- **主要行为**：<按用户视角描述交互、状态变化或调用结果。>
- **成功结果**：<用户或调用方最终观察到什么。>
- **失败与边界行为**：<无权限、空状态、重复操作、部分失败或其他真实边界下会观察到什么。>
- **兼容要求**：<既有用户、调用方或数据必须保持的行为；不适用时删除。>

#### 2.1.3 Scope Boundaries / 分项范围边界

- **本项包含**：<本分项负责的产品结果。>
- **本项不包含**：<容易被误认为属于本项、但明确由其他分项负责或本次不做的内容。>
- **引用共享规则**：<引用 `1.3` 中适用的规则；没有则删除。>

#### 2.1.4 Validation Mapping / 验收映射

- `VAL-<完整语义分类>-<NNN>`：<该验收断言证明本分项的哪个可观察结果>

## 3. Overall Out of Scope / 整体不做

- <不属于任何分项、但容易被误认为包含的整体能力。>

## 4. Open questions / 悬而未决

> 可选。格式：`<问题> — 归属：arch / plan / impl；推迟理由：<为什么不影响当前产品契约确认>`。

## 5. References / 参考资料

> 可选。列出实际影响本规格的外部链接、原型或项目资料。
```
