# `spec.md` 模板

按技能的写作原则写；下面的骨架是唯一详细契约。未标“按需”的是必填；标“按需”的没有内容就整节或整行删除，不写“无”。

存放：未拆分时写 `docs/specs/<topic>/spec.md`，与 `validation-contract.md`、`validation-results.md` 同目录；拆成子规范时本文件是总规格，与 `umbrella.md` 配套，子规范放在同一目录的子目录；跨多个拉取请求且用户确认长期生命周期时改用 `docs/long-running-specs/<topic>/`。

使用约定：

- 标题用中文，代码实体名照原样，最多四级；交叉引用写带名字的链接，不写裸章节号。
- **产品结构**：有产品需求文档时沿用它的页面或功能点结构和名称；没有时按用户可感知的子功能组织，不按模块、接口、数据表或实施步骤划分。
- **与产品需求文档分工**：有产品需求文档时，“为什么做”只写几句并链接它（含版本日期），不复述背景、竞品和视觉稿；文案、规则、数值和异常结果这些实施依据仍写进规格。没有时，“为什么做”用几句话写清问题、证据和替代方案，来源写用户原话。
- **只写可观察的行为**：代码常量名、内部组件、实施单元和 Agent 分工属于架构设计和计划。
- **图优先**：页面流转、状态转换和跨角色的流程能画图就画图（流程图、状态图、时序图），图里写用户或调用方看得到的含义；规则、异常和文案仍用表核对。
- **规则只定义一次**：跨叶子的产品规则写在要点里，编号 R1、R2，叶子按编号引用。
- **文案**：生产级用户表面写出本次新增或改变的全部文案。文案归负责它的规格：服务端下发或配置的写在服务端规格，客户端固定的写在客户端规格。
- **平台类和技术类需求**：用户是调用方或开发者时，场景表写调用方的动作和可观察结果，不硬套界面字段。
- **状态与修订**：可先保存标明“待评审”的草稿，待确认问题不能作为实施依据；修订直接改正文，确认后在确认记录加一行。已确认版本的待确认表只保留有意交给架构、计划或实现的问题，写明归属与推迟理由；确认后才发现、需要产品拍板的问题也写进去，并在状态行写明哪部分待确认。
- **拆成子规范时**：总规格的叶子写父级验收编号；子规范各自配验收契约，总规格不另建。
