# `spec.md` 模板

文件化规格触发时，将下面的模板复制到 `docs/specs/<topic>/spec.md`。跨多个 PR 的总规范只有在用户明确确认长期生命周期后，才写入 `docs/long-running-specs/<topic>/spec.md`；当前子 PR 仍维护自己的规格。

使用约定：

- 保留双语章节标题，正文使用对话语言。
- 删除写作提示和占位符；不适用的可选章节直接删除，不用“无”填满形式。
- 只记录确认后的价值、事实和行为，不保存逐题问答流水。
- `Open questions` 只保存有意交给架构或实施阶段的决定，并写明归属和推迟理由；未解决的产品歧义必须回到需求澄清。

```markdown
# <主题> — Spec（<主题> — 规范）

> <一句话说明要为谁解决什么问题。>

## Why (为什么做)

- **问题与用户**：<谁在什么场景遇到什么问题。>
- **事实依据**：<用户反馈、使用数据、当前行为、故障或其他证据。>
- **价值与时机**：<为什么值得现在解决；预期改善什么结果。>
- **替代方案**：<为什么不选择不做、人工处理或更小方案。>

## Findings (调研发现)

> 可选。只写与需求决定有关的当前事实，每项锚定代码、接口、数据、文档或外部来源。

<事实与来源>

## What (做什么)

> 写用户可观察的行为、成功结果和失败语义。停在技术结构与实施步骤之前。

<行为契约>

## Out of scope (本次不做)

- <容易被误认为包含、但本次明确不做的内容。>

## Open questions (悬而未决)

> 可选。格式：`<问题> — 归属：arch / plan / impl；推迟理由：<为什么不影响当前产品契约确认>`。

## References (参考资料)

> 可选。列出实际影响本规格的外部链接、原型或项目资料。
```
