# spec.md 模板

将本模板复制到 `docs/specs/<topic>/spec.md` 并填充每个 `<占位>`。与 `validation-contract-template.md` 配套使用（拆分时还配套 `umbrella-template.md`）。

**语言规则**：下面的 section 标题是双语的（英文锚点 + 中文提示），必须逐字保留——工具和审查者会 grep 英文锚点。**正文内容（每个标题下的散文）必须用用户的对话语言来写。** 对话是中文，就把 Why / Findings / What 各节写成中文；是英文就写英文。不要混写。

不要删掉可选章节（`References`、内容稀少时的 `Findings`、`Open questions`）——如果确实没有内容，留一行"无"，免得后来的读者怀疑这节是不是被忘了。对 `Open questions` 来说，空的"无"对一份澄清充分的 spec 是正常且常见的结果——不代表工作没做完。

```markdown
# <feature> — Spec (<功能> — 规范)

> 一句话概括这个 spec 在做什么（可选但推荐）。

## Why (为什么做)
<1–4 段：动机、要解决的痛点、灵感 / 已有方案 (如有)。>

## Findings (调研发现)
<A1 调研阶段已经发现的事实，列表呈现 (描述"当前是什么样"，不写"将来要怎么做")。每条都锚定到具体来源：文件路径、commit、文档、外链。>

## What (做什么)
<外部行为契约。当涉及面较广时可拆多个子节 (### 1. …, ### 2. …)。停在实现线之上，不要写"用哪个文件 / 哪个函数 / 哪个库"。>

## Out of scope (本次不做)
<显式列出"本 spec 不做 X / Y"，必要时附简短理由。>

## Open questions (悬而未决)
<本 spec **有意**留给 plan / 实现阶段决定的问题。不是未澄清需求歧义的停车场——若问题是关于"用户想要什么"且尚未回答，回 A2 澄清循环，不写这里。每条**必须**写明归属（plan / impl）与推迟理由；两者都写不出，就不算悬而未决项。编号列表；没有则写"无"——这是正常结果。>

## References (参考资料 — 可选；澄清期间用户给过任何外链时必填)
<外链列表 + 来源时机 + 对设计的影响要点。>
```
