# `validation-contract.md` 模板

按技能的写作原则写；标“按需”的没有内容就删除。与 `spec.md` 同目录；拆成子规范时每个子规范目录一份，总规格不另建。一条验收是一项断言，不是一个测试用例，实现时可以按风险展开为多个用例。

使用约定：

- 与 `spec.md` 用相同的叶子名称和顺序，每个叶子一张表；新增、合并或改名叶子时同步。
- 编号 `VAL-<完整语义分类>-<NNN>`：分类用完整、稳定的英文单词，不用自造缩写；同一行为领域复用分类并连续编号。“验收什么”一列以简短中文标题开头。
- “验收什么”只表达一个可观察结果，不能让两种明显不同的行为都算通过；“通过标准”写什么结果算通过，不复述要求，不写测试函数、夹具、模拟方式或实施步骤。
- **证据**：同一叶子的证据类别相同时在叶子标题下写一次；不同时才在表里加“证据”列，不逐行重复同一句。按风险选最直接的证据，例如仓库检查、单元、组件、契约、集成、HTTP、界面自动化、运行探测或端到端；这是开放示例，具体工具交给 `test-driven-development`。
- 客户端或前端的正确性依赖真实界面、系统权限或运行时集成时，至少保留一条代表性真实界面验收，可以用界面自动化，或由 Agent 通过 MCP、命令行驱动模拟器、真机或浏览器；新增或改变的服务端接口行为至少有一条 Agent 可执行的 HTTP 测试或接口端到端验收。其余断言用更直接的分层证据。
- 关键状态、危险操作、错误恢复和用户可见文案按真实风险形成断言；同一状态里不可分割的文案可以一起验证；服务端下发的文案可以用接口契约或 HTTP 测试证明。
- 优先 Agent 验收；人工验收只作例外，必须写明无法可靠自动观察的原因、要人判断的内容和操作入口。
- 子规范的契约在“验收什么”里写“承接父级 VAL-……”；父级到子规范的映射只在 `umbrella.md` 维护。
- 本文件只定义通过标准，执行结果写在 `validation-results.md`。

````markdown
# 验收契约 — <主题>

> 与 spec.md 配套：spec.md 写为什么做、做成什么样；本文件写什么算通过。

## 代表性验收路径（按需）

> 只在需要驱动真实界面或跨层协作时写入口、关键操作和可观察结果；一条路径可以覆盖多个叶子。

- <路径>：<覆盖哪些叶子>

## <与 spec.md 一致的叶子名称>

证据：<证据类别；需要真实界面时引用上面的路径>

| 编号 | 验收什么 | 通过标准 |
|---|---|---|
| VAL-<CATEGORY>-001 | <简短中文标题：单一可观察结果> | <什么结果算通过> |

叶子内证据类别不同时：

| 编号 | 验收什么 | 通过标准 | 证据 |
|---|---|---|---|
````
