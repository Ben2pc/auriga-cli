# `umbrella.md` 模板

按技能的写作原则写；未标“按需”的是必填，标“按需”的没有内容就删除。只在需求确实拆成多个可独立确认、独立验收、不误导总体目标的完整用户结果时使用；模块数、文件数、代码行数和实施手法不是理由。

总 `spec.md` 是完整产品需求和父级验收编号的唯一来源。`umbrella.md` 只保存跨子规范协调需要的内容：子规范清单、父子验收对应、真实依赖、状态和生命周期；不复制总规格正文，不另建总体验收契约。

目录：

```text
docs/specs/<总主题>/                # 跨多个拉取请求且用户确认长期生命周期时用 docs/long-running-specs/<总主题>/
├── spec.md
├── umbrella.md
├── arch_design.md               # 总设计（按需）
└── <子主题>/
    ├── spec.md
    ├── arch_design.md           # 子设计（按需）
    ├── validation-contract.md
    └── validation-results.md
```

使用约定：

- 子规范按可独立交付的完整用户结果划分，可以承接总规格的一个或多个分项，不要求与总规格章节一一对应。
- “顺序”只表达真实交付依赖；没有先后依赖写“并行”。
- 子规范在自己的 `validation-contract.md` 里写子验收项；本文件只维护父级到子规范的映射，不另造断言。
- 跨子规范的交付边界和协调验收可以写；详细实施步骤和 Agent 分工交给 `incremental-impl`。
- 子规范归档或晋升时由 `documentation-management` 执行，并把链接改成实际有效位置；验证结果按次交付归档。长期规范不替代子拉取请求的待评审流程，全部子拉取请求结束后由人工决定归档或晋升。
- 子规范状态变为“已上线”时，按 `arch-design` 交接一步原位瘦身它的子设计；这是压缩，不是清理或迁移。

````markdown

> <一句话：这些子规范共同为谁交付什么完整结果。>

## 1. 共同范围

- **总体结果**：<完成后整体可观察的结果>

## 3. 父子验收对应

| 父级验收项 | 子规范 | 子验收项 | 状态 |
|---|---|---|---|
| `VAL-<CATEGORY>-001` | [<子主题>](<子主题>/validation-contract.md) | `VAL-<CHILD>-001` | 未执行 / 通过 / 失败 / 不适用 |
````
