# 架构设计

planning 阶段的 skill,只做**架构层面的概要设计**。spec 定了"做什么",这个 skill 定"怎么做"——但只到架构层面(模块、依赖、分层、接缝),不下沉到代码细节。之后由 `incremental-impl` 把设计切片落地。

```
spec-design          →   arch-design          →   incremental-impl
(为什么 + 做什么)         (怎么做 —— 本 skill)        (切片 + 实现)
```

**为什么需要这一步**:软件有两份价值——它现在的行为,和它未来改起来有多便宜。后者就是架构。架构设计的目的不是"现在能跑",是让系统保持"软"。这条立意同时反对两件事:**草草不设计**(欠下的债未来加倍偿还)和**过度设计**(为想象中的需求堆抽象,每一层都要在以后每次阅读代码时付利息)。这个 skill 的每条规则,都服务于在这两者之间找到"刚好够"的设计。

## 什么时候用

两个独立入口都进这个 skill,都在**架构高度**:

| 入口 | 触发 | 上游输入 |
|---|---|---|
| **新功能架构设计** | 一个新功能走完 `spec-design`,规模分诊判定它跨边界、或验收标准超过 5 条、或跨模块,需要真正的设计 | `docs/specs/<topic>/spec.md` + `validation-contract.md` |
| **既有系统架构升级** | 一段已有代码结构有问题,想改进它的架构,但**不改变对外可见行为** | 目标代码 + 一句具体的结构抱怨 |

也在用户说"技术方案 / 架构设计 / 架构升级 / 重构方案 / 模块怎么拆 / 怎么分层 / 这块架构怎么改",或你即将开始一个跨模块改动而"怎么做"并不显然时触发。

**不要用于:**

- **需求澄清**——如果"做什么"还模糊,先回 `spec-design`。这个 skill 假定"做什么"已经定死。
- **切片与执行细节**——规模分诊、切片、分发、实现-测试-验证-提交的循环,归 `incremental-impl`。
- **有复现步骤的 bug**——复现步骤本身就是需求,走 `systematic-debugging`。
- **模块或文件内部的代码级清理**——命名、嵌套、死代码这类局部清理归 `code-simplify`。
- **琐碎的单模块改动**——如果快速开发流程的三个判据都成立(单模块、验收标准 ≤ 5 条、无跨边界接口改动),就没有架构可设计,直接去实现。不要为了显得周全而制造设计流程。

## 四条铁律

**一、设计是"怎么做",不是"做什么"。** 这个 skill 不重开需求的动机和范围。如果打磨设计时发现"做什么"其实还含糊,停下,回 `spec-design`——不要用一个随意的设计决策把需求的窟窿填上。被设计决策填掉的需求窟窿,等于悄悄发明了一个需求。

**二、架构升级不改变对外可见行为。** 既有系统升级这条路,保留一切用户、外部调用方、接口消费方、下游文件格式能观察到的东西。如果结构改动**会**改变可观察行为,那一部分是新功能——拆出去走 `spec-design`,只有不改行为的结构改动留在这里。(这正是 Fowler 对"重构"的定义。)

**三、推荐方案是满足设计驱动的最简方案。** 选更重的方案,只有在能**点名一个具体的设计驱动**要求它时才允许。"以后可能要"不是驱动。这是 auriga 的"如无必要,勿增实体"用在设计阶段——这里加的每一层、每一个抽象、每一次间接,都要由未来每一次阅读代码的人偿还。

**四、抽象要有明确理由。** 引入任何抽象(接口、间接层、适配器)都必须说得出一个明确、具体、当下成立的理由——通常是"接缝两侧确实是不同变化速率的真实边界"(区域差异、第三方可替换、易变对稳定)。说不出明确理由就不抽。判断标准是**接缝两侧变化速率是否真的不同**,不是"以后会不会有第二种实现"。
- 配套规则:只有一种实现时,多半不需要为它抽接口——一个适配器只是假想的接缝,两个才是真接缝。
- 例外:如果接口买的是"依赖方向"或"变化隔离"(比如业务逻辑不该直接依赖某个具体数据库),即使现在只有一种实现也值得——它买的不是"多实现",是把不可逆决策隔在边界后面。

## 流程

```
A. 调研        →  B. 设计候选        →  C. 选型与记录        →  D. 自检与交接
   (摸清现状)       (出方案、做权衡)       (选方向、磨细节、落库)     (自检与交接)
```

### A 调研

**A1. 接收输入。**
- 新功能:完整读 `spec.md` + `validation-contract.md`。留意用户在 `spec-design` 阶段顺口提过的"怎么做"——`spec-design` 故意把实现提示挡在 spec 之外,它们在这里作为设计输入重新浮现。
- 既有系统:读目标代码本身,不是读它的摘要。打开文件。让用户用一句话说清结构抱怨。

**A2. 摸清现状。**
- 新功能:新代码接到哪里——哪些模块、哪些接口、数据怎么进出、会动到哪些已有代码。
- 既有系统:把受影响区域的当前架构画出来——模块、依赖方向、分层、数据流。要具体到文件路径,不要用形容词。

**A3.(既有系统)给结构问题精确定性。** 没有命名的问题的重构是漫无目的的打磨。用诊断工具(见下文「诊断工具」)给它定性:是上帝模块、循环依赖、浅模块转手层、放错层,还是边界没对齐变化轴。**命名后的问题就是验收标准**——这个设计的成败,看它有没有除掉**那个**问题,不看代码"是不是变顺眼了"。

**A4. 规模退出——太小就退出。** 拿现在掌握的信息重新跑快速开发流程的三个判据:单模块、验收标准 ≤ 5 条、无跨边界接口改动。三个都成立,就没有架构可设计——说明这一点,交回直接实现,退出。规模门是一道门,不要为了显得周全而虚构设计工作。

### B 设计候选

**B1. 框定设计问题。** 在生成方案之前先把决策空间摆明:
- **设计驱动**——挑出此处真正重要的 2–4 个质量属性(见「设计驱动词汇表」)。不要拿全部属性去打分;"什么都重要"的框架等于没有决策。
- **约束与不变量**——什么**不能**变:验证契约(新功能)、对外行为契约(既有系统)、公共接口、性能预算、平台限制。
- 切模块时,**沿"变化的轴"思考边界**:什么会因为同一个原因、在同一时间一起变,就把它们放在一起;因不同原因而变的,就切开。这是"单一职责"真正可操作的说法。

**B2. 出 ≥ 2 个真候选。** 每个候选都得是一个称职的工程师真会为它辩护的方案——不要造只为了输的稻草人。永远包含**最简候选**(满足设计驱动的最小结构改动);既有系统这条路,"什么都不做 / 就地小修"是一个合理的最简候选。每个候选都勾出:模块形状、关键接口、数据流。

**B3. 权衡对比。** 候选 × 驱动,列一张表。每个格子写**具体后果**,不写评级("动到 3 个模块 + 2 套测试",不是"影响半径:中")。这张表是为了让被否决方案的代价看得见,不是为了机械算出一个赢家。

**B4. 最简审查。** 拍板之前:领先的候选是不是满足驱动的最简方案?如果赢家是更重的那个,用一句话写清是哪一个驱动撑得起这份额外重量;写不出来,简单的那个赢。同时判断**真重复还是假重复**:两段代码现在长得像,不代表该合并成一个模块——如果它们因不同原因演化,强行抽取会在未来制造耦合。

### C 选型与记录

**C1. 用户选方向 + 一起打磨。** 把候选和权衡表摆给用户,**用户选方向**。选定后进入打磨:和用户一起走设计树——依赖方向、接缝放在哪、接口长什么样、哪些测试能留下——一项项敲定。架构决策不该 agent 闷头拍,但也不该像 `spec-design` 那样一问一答(那个节奏对"挑方向"太碎)。

**C2. 定迁移路径与保护网。**
- 既有系统:定**迁移形态**——用哪种结构策略从现状走到目标态(见下文「迁移形态」)。
- 既有系统:定**行为保护网**——动任何结构之前,受影响的对外行为必须有测试盖住。已覆盖就记下是哪个套件;没有,先补特征测试。特征测试是重构版的"红"阶段:不是规定新行为,是锁住既有行为,让重构没法悄悄改掉它。行为面不显然时,特征测试的设计可借 `test-designer`。
- 新功能:如果发现现有结构挡路,设计本身要包含一段**前置的准备性重构**——先让改动变容易,再做这个容易的改动,而不是硬塞一个别扭的设计将就。
- **不产出实施顺序**:各部分以什么顺序、切多大粒度落地,是 `incremental-impl` 的事;arch-design 交付的是设计,不是执行排序。

**C3. `arch_design.md` 闸门。** 见下文「`arch_design.md` 闸门」决定要不要落库。要落,就照 `references/arch-design-template.md` 写 `docs/specs/<topic>/arch_design.md`。拿不准就问用户。

### D 自检与交接

**D1. 自检**——坐到将要实现这个设计的人的位子上,过一遍下文「自检清单」。当场修,不要重做前面的阶段。

**D2. 提供架构总览(仅当 `arch_design.md` 已落库)。** 闸门触发、文档写好后,用 `AskUserQuestion` 给用户三个选项,方便他快速过一眼这个架构——顺序固定为 跳过 → playground → 静态 HTML:
- **跳过**——直接进 D3。设计小、用户已在对话里看清时的默认。
- **playground**——派 `playground:playground`(Anthropic 官方插件)以 `arch_design.md` 为输入生成一个交互式 HTML,可视化地浏览候选、权衡与依赖图。playground 插件没装时,隐藏这个选项。
- **静态 HTML 总览**——生成自包含的 `docs/specs/<topic>/arch-overview.html`,把 `arch_design.md` 渲染出来:Mermaid 模块图、目录树、候选权衡表都画出来,然后 `open` 它。不依赖任何插件。

闸门没触发(对话内拍板、没写文档)时,跳过这一步——没有文档可总览。

**D3. 交接。**
- 设计(落库的 `arch_design.md`,或闸门没触发时的对话内决策)作为规划输入交给 `incremental-impl`。
- 既有系统这条路额外交接保护网要求:特征测试在第一个结构性提交**之前**已存在且为绿。
- 如果在 A4 已经退回直接实现,那就没有要交接的——这是一个合法的结果。

## 诊断工具(给既有系统升级用)

判断"这块架构到底有没有问题"要可操作,不能靠"我觉得乱"。两类工具配合用——**清单负责广度(别漏看),删除测试和深浅模块负责准度(别冤枉)**。

**删除测试**:假想把某个模块删掉,它的代码直接 inline 进所有调用方。
- 复杂度就这么消失了 → 它本来就是个没必要的转手层,该删。
- 复杂度在好几个调用方那里重新冒出来、而且重复了 → 它在干活,是个好模块,别动。

**深模块 / 浅模块**:深模块 = 接口窄、背后行为多,用一点接口换很多功能;浅模块 = 接口几乎和实现一样复杂,包了一层却没替调用方省事。

**召回清单(架构层面的问题信号)**:
- **循环依赖**——模块依赖图里出现了环。
- **依赖方向倒错**——稳定 / 高层的模块依赖了易变 / 低层的模块。
- **放错层**——一段逻辑待在不该待的层。
- **上帝模块**——一个模块什么都管。
- **浅模块 / 转手层**——包了一层却没省事(用删除测试确认)。
- **跨接缝泄漏**——实现细节漏过接口,被调用方依赖上了。
- **发散式变化**——一个模块因为多种不同原因而改;边界太粗,该拆。
- **霰弹式修改**——一个改动要同时动很多模块;相关的东西被切散了,该聚。
- **依恋情结**——一段逻辑总在操作别的模块的数据;它放错模块了。

后三个是"模块边界没对齐变化轴"的直接信号,和 B1 的"沿变化轴切模块"是一体两面。

**真接缝规则**:一个适配器只是假想的接缝,两个才是真接缝。见铁律四。

## 设计原则(出自《架构整洁之道》)

切模块、定依赖方向时的准则:

- **依赖规则**——源码依赖一律指向更稳定、更抽象、更高层策略的一侧。业务规则不依赖框架、数据库、界面。**框架、数据库、界面、第三方都是"细节"**,放在架构边界的外圈;核心业务策略不 import 它们。
- **边界划在变化速率的断层上**——把变化快的(框架、数据库、界面、第三方)和变化慢的(业务策略)隔开。
- **沿变化轴切模块**——一个模块只对一个"变更来源"负责。注意是变更来源,不是"只做一件事"。
- **无环依赖**——模块依赖图里不能有环。
- **划边界是为了推迟决策**——好架构尽量少做不可逆决策,把不可逆的(选数据库、选框架)隔在边界后面,能推迟就推迟,保留可选项。
- (可选)**按业务能力组织目录**,而不是按技术分层——让人一眼看出"这是个什么系统"。

> 要做组件 / 模块的划分(尤其工程已经是多组件的大工程),读 `references/component-design.md`——里面有组件内聚与耦合原则,以及移动端模块化的落地提示。

## 接口设计(架构层面的四条)

切模块就会定义模块之间的**接缝**,也就是接口。接口设计有一部分是架构决策,跑不掉——架构层面取这四条:

1. **窄接口 / 信息隐藏**——接缝上凡是可观察的,迟早会被调用方依赖(Hyrum 定律)。接口只暴露调用方真正需要的,藏住实现。这其实就是"深模块"换个说法。
2. **契约先于实现**——接缝的接口在走设计树那一步就定下来,别边写边长出来。
3. **演进靠加不靠改**——接口要变,优先加可选项,别改签名、别删字段;这直接关系到影响半径。
4. **One-Version**——同一个依赖、同一套接口在一个系统里只留一个版本;多版本并存会引发钻石依赖,把依赖图搞乱,和「无环依赖」同属一类问题。

> 接口落地时的实现细节——错误语义、边界校验、REST 资源形态、命名规范、TypeScript 类型模式——见 `references/interface-design.md`。那份手册以实现细节为主;定接口契约时也用得上它前半的根本心法与演进部分。

## 设计驱动词汇表

挑此处真正重要的 2–4 个。点名它们,才把"我喜欢这个"变成站得住的选择。

| 驱动 | 它在问什么 |
|---|---|
| 简单性 | 最少的活动部件,读者一次要记住的概念最少 |
| 影响半径 | 改动波及多少模块、测试、调用点 |
| 可测试性 | 新结构能不能隔离测试;它增加还是减少了测试接缝。**难测本身就是架构问题**——一个设计若只能靠端到端验证,接缝放错了 |
| 可逆性 | 万一选错,退出来有多贵。好架构尽量少做不可逆决策 |
| 一致性 | 是否沿用了代码库里已有的模式 |
| 迁移成本 | 走到目标态要几步、有没有中间破碎态、要不要协调 |
| 性能 | 延迟 / 内存 / 吞吐——**只在有明确预算时**才作为驱动 |
| 扩展性 | 下一个"已在路线图上、确定要做"的改动的成本——绝不是假想的改动 |

扩展性是个陷阱:它在抽象层面能为几乎任何抽象辩护。只有当一个具体的、近期的、已经明确的改动点名它时,才允许它作为驱动。

## 迁移形态(既有系统升级)

既有系统从现状走到目标态,选一种迁移方式,写进 `arch_design.md` 的「Decision & Rationale」。三种形态按"替换对象"和"规模"区分:

| 迁移形态 | 替换对象 | 新旧关系 | 怎么过渡 | 典型场景 |
|---|---|---|---|---|
| **并行变更** | 一个接口 / 契约 | 新旧接口并存 | 先加新接口 → 调用方逐个迁 → 删旧接口 | 改函数签名、接口形状、数据结构;尤其调用方不在你控制下 |
| **抽象分支** | 一个模块的实现 | 新旧实现满足**同一接口**,可互换 | 插中间层 → 背后建新实现 → 翻转中间层 → 删旧实现 | 一套代码里替换某模块的实现(换库、换算法) |
| **绞杀榕** | 一整个系统 / 子系统 | 新系统**独立重建**,形状可不同 | 前面加路由分流 → 功能逐块在新系统重建并切流量 → 旧系统清空后删除 | 替换大型遗留系统,不能停机、不敢一次性大改 |

怎么选:改的是接口 → 并行变更;换模块实现、新旧能套同一接口 → 抽象分支;换整个系统、新旧不是一个形状 → 绞杀榕。

不论哪种,每一步都要让系统保持可编译、可测试、可发布,且独立可回滚(延伸自 `git-workflow` 的原子提交规则)。

## `arch_design.md` 闸门

`arch_design.md` 是一份带版本的设计文档,它的价值在于让**另一个** agent(或几个月后的你)不必重新推导就能执行或扩展这个设计。这份价值只有在设计本身不平凡、且会活过当前这轮对话时才成立。所以它是**有条件**产出的。

**满足任一条,就写 `arch_design.md`:**

- 设计跨了模块或子系统边界——动其中一部分的 agent 需要看到全局。
- 有 ≥ 2 个候选带着实质性的权衡——把被否决的候选和**理由**记下来,能阻止未来的 agent 重新议一个已经定了的决策。
- 引入新子系统、新分层,或改动了共享模块 / 公共接口的结构。
- 实现会被切片分发(`incremental-impl` 的 L 规模 / 并行)——每个切片需要一份共享的设计参照。
- (既有系统)迁移跨多个提交,中途接手的 agent 需要看到目标态和当前步。

**跳过文档、对话内拍板即可,当:**

- 单模块、方案唯一且显然(这种应该在 A4 就退出了)。
- 设计三两句话能说清,而且**同一个** agent 马上就实现。一份没人会回头读的文档纯属负担。

**拿不准——问用户。** 当设计是中等分量、你确实判断不了,用 `AskUserQuestion`:给出"写 `arch_design.md`(会被交接或日后回看时推荐)"对"对话内推进(更快,不留要维护的文档)",并说明权衡。不要默默选边。

**位置与生命周期。** 文档落在 `docs/specs/<topic>/arch_design.md`——和 `spec-design` 用的是同一个临时工作区,`pr-ready-guard` 会在 PR Ready 前强制它有个去向。到 PR Readiness 阶段,按 CLAUDE.md 的「文档约定」处理:如果它是长期参照(模块布局、数据流——正是那个目录装的东西)就提炼进 `docs/architecture/`,否则归档进 worklog 或删除。

**它的"候选方案对比"那一节**借用 ADR 模板的写法——每个候选带 优点 / 缺点 / 否决理由,最后一节写"后果"。模板见 `references/arch-design-template.md`。

**语言。** `arch_design.md` 是一份计划文档——正文用对话所用的语言写(中文对话就写中文)。章节标题保持模板给的样子(英文锚点 + 中文提示),结构性关键词保持英文。

**ADR 是可选的边缘产出,不是常规动作。** 只有当某个决策"昂贵到难以逆转"(选了某个数据库、定了某种鉴权架构这类),才在收尾时问用户要不要把它固化成一条 ADR——ADR 是存档,作为后续开发的架构指南。固化这个动作**交给 `documentation-and-adrs` skill**,这个 skill 不自己重造 ADR 那一套。`arch_design.md` 是开发过程中的方案,ADR 是长期档案,两者分工不重叠。

## 自检清单(D1)

坐到将要实现这个设计的 agent 的位子上读一遍。当场修,不要重做阶段。

- [ ] 写明了设计问题和它的驱动——不只是选定的方案。
- [ ] 真考虑过 ≥ 2 个候选;被否决的有记下来的理由。
- [ ] 推荐方案是满足驱动的最简方案,否则点名了那个撑得起额外重量的驱动。
- [ ] spec 或行为契约里的每条不变量 / 约束,都被选定的设计保住了。
- [ ](既有系统)A3 命名的那个结构问题,被这个设计真正除掉了——不是挪了个位置。
- [ ](既有系统)行为保护网在第一个结构性步骤之前就已指定。
- [ ] 没有夹带实施顺序或切片计划——那是 `incremental-impl` 的。
- [ ] 没有把"做什么"层面的决定(新行为、范围变化)当成设计选择夹带进来。
- [ ] 如果写了 `arch_design.md`:没有 TBD / 占位符;一个零上下文的 agent 能照着执行。

## 反模式

- ❌ "做什么"还没定就开始设计——spec 模糊就回 `spec-design`,别用一个随意的设计决策把窟窿填上。
- ❌ 把行为变更夹带进重构——既有系统升级是不改行为的;行为变更是新功能,要走 spec。
- ❌ 造稻草人候选——只为输而造的候选让"对比"变成演戏。每个候选都得站得住。
- ❌ 漏掉最简候选——桌上没有一个"少做点"的选项,设计就会默认越长越重。
- ❌ 拿全部驱动去打分——"什么都重要"的框架等于没有决策。挑 2–4 个。
- ❌ 用假想的未来需求给结构辩护——扩展性必须由一个具体的、近期的、已明确的改动点名。
- ❌ 给一个琐碎的单模块改动写 `arch_design.md`——闸门是一道门;没人回头读的文档是负担。
- ❌ 一个会被切片分发的跨模块设计却跳过 `arch_design.md`——切片之间会各自重新推导设计,然后漂移。
- ❌ 在这里产出实施顺序或切片计划——arch-design 交付设计;顺序、切片、分发是 `incremental-impl` 的。
- ❌ 重构却没有命名的结构问题(A3)——"弄干净点"不是目标,设计无法判定完成。
- ❌ 既有系统升级,特征测试还没绿就动第一个结构性提交——重构就能悄悄改掉行为而没东西接得住。

## 和其他 skill 的关系

- `spec-design`——新功能入口的上游,提供 `spec.md` + `validation-contract.md`。它故意挡在 spec 外的"怎么做",是这个 skill 的输入。
- `incremental-impl`——下游消费者,拿这个 skill 的设计,负责规模分诊、切片、分发、实施顺序、单切片循环。
- `test-designer`——既有系统保护网的特征测试,在行为面不显然时由它设计;新功能则由它对着验证契约设计失败测试。
- `playground:playground`(Anthropic 官方,软依赖)——D2 架构总览的辅助选项之一;没装就只提供静态 HTML 总览。
