# 架构设计

`arch-design` 在实现前澄清系统如何表达需求，既服务新功能，也服务现有架构和领域模型的主动优化；产物是便于人评审的设计依据，不是一套架构教材。

三类产物各有边界：

| 阶段 | 澄清内容 |
|---|---|
| `spec-design` | 为什么做、用户可观察的行为和验收契约 |
| `arch-design` | 领域概念、职责、模块边界、依赖方向、关键接口、数据流和技术质量目标 |
| 计划与 `incremental-impl` | 实施步骤、切片、顺序、分发和提交 |

## 什么时候使用

- 新功能存在需要确认的职责边界、数据所有权、接口兼容或迁移形态决定。
- 用户要求优化现有架构、重新分层、调整依赖或规划系统演进。
- 用户要求领域建模、改善领域模型，或概念、职责、规则和生命周期尚未归位。
- 结构选择会实质改变关键数据流、行为保护方式或长期演进成本。

以下情况退出：

- 产品语义、范围或用户可观察行为仍不清楚：回到 `spec-design`。
- 有明确问题验证路径的缺陷：先走 `systematic-debugging`。
- 只是模块内部的命名、嵌套、重复、死代码或局部搬移：交给 `code-simplify`。
- 调研后确认沿用现有架构即可、没有实质性的架构或领域决定：说明理由，直接进入后续实现；跨多个文件或模块本身不触发完整设计。

## 核心约束

1. **先澄清，再实现。** 实质架构决定在实现前取得用户确认；复用对话中仍有效的已确认设计，只对新增或改变的实质决定重新确认，不用代码草稿替代确认。
2. **区分产品决定与技术决定。** 架构澄清若暴露出未确定的产品语义或外部行为，回到需求规格补充；纯技术表达方式留在本技能中确认。
3. **从真实代码出发。** 阅读受影响代码、现有接口和数据流，不根据摘要想象当前结构。
4. **选择满足当前驱动的最简设计。** 抽象、替换点和新层级都要有当下成立的理由，不用假想需求证明复杂度。
5. **只比较真实选项。** 只有存在会显著改变成本、风险或行为保护方式的真实取舍时才给出多个候选；方向明确时直接给出推荐方案和理由。
6. **先给决策页，再写分项。** 评审者先看到改什么、核心决定、代价和待确认项，再读按需求主题组织的分项。

## 写作原则

1. **首要读者是评审者**，其次是实施的 Agent；优先于“未指定读者时面向 Agent”的通用默认。
2. **先给重点**：首屏让评审者不往下读也能拍板。
3. **一事一处**：每个决定、规则、模型、接口和事实只定义一次，其他位置用带名字的链接或规则编号引用。
4. **只写要评审的内容**：规格不写技术方案和实施过程，架构设计只写跨边界契约和需要拍板的选择。
5. **图和表优先于段落**：关系、流程和状态画图；核对类内容用表，第一列放被核对的对象。
6. **用中文常用说法和短句**；按需字段没有内容就删，不写“无”。
7. **修订直接改正文**，历史交给版本库。
8. **篇幅与改动规模相称**：小改动只有首屏和一两个分项。

## 流程

### 1. 建立设计上下文

- 新功能读取对话内规格或已有的 `spec.md`、`validation-contract.md`、适用的上级规范与已确认决定；现有系统直接读目标代码和相关测试。已读且仍有效的上下文直接复用。目标范围不清时先确认要处理的模块或结构问题，不猜测扫描区域。
- 写清当前结构、具体问题、设计目标和不做什么。领域模型优化要同时写清概念混乱、职责错位或规则泄漏发生在哪里。
- 收集项目级架构规则：用 `git rev-parse --show-toplevel` 确认仓库根，读取 `<仓库根>/docs/rules/arch/` 下与本次设计相关的规则；再从每个受影响代码或规范路径向仓库根查找更近的 `docs/rules/arch/`。两层都读取，冲突时以离目标代码最近者为准；非 git 仓库时从目标路径向当前目录回退查找。没有相关规则时记录“无项目专属架构规则”。

### 2. 按条件唤醒设计工具

只读本次需要的参考资料：

| 设计条件 | 参考资料 | 提醒考虑什么 |
|---|---|---|
| 划分组件、包或功能模块 | `references/component-design.md` | 内聚、耦合、依赖方向和物理模块边界 |
| 设计公共接口、模块边界或接口演进 | `references/interface-design.md` | 信息隐藏、契约形状、兼容性和错误语义 |
| 优化领域概念、职责、规则或生命周期 | `references/domain-modeling.md` | 实体、值对象、聚合、领域服务、事件和状态模型 |
| 替换接口、实现、模块或遗留子系统 | `references/migration-strategies.md` | 显式切换、并行变更、抽象分支、绞杀榕和保护网 |

参考资料是工具箱，不是必做清单。

### 3. 澄清设计

按本次设计的相关性明确：

- 当前问题、目标、不做什么，以及现有行为、公共接口、平台和项目规则带来的硬约束。
- 领域概念、职责、数据所有权、模型的类型与代码位置；本次结构变化及非显然选择的理由。
- 目标模块边界、依赖方向、关键接口和数据流；每条权威需求由哪个机制承接、落在何处、用什么证据验证。
- 影响架构选择的技术质量目标、设计响应及真实代价，不按通用清单补齐。
- 现有行为的保护方式、迁移中间状态、切换与回滚约束。

### 4. 写出可人工评审的设计

存在实质性的架构、领域模型或跨边界决策时，按 `references/arch-design-template.md` 写入 `docs/specs/<topic>/arch_design.md`；模板是唯一详细契约，写作时读取。仅在触发退出条件或用户要求只在对话内确认时跳过文件，对话内仍须给出足以评审的契约和理由。无法写入时报告阻塞并在对话中给出草稿，草稿不作为已确认的实施输入。

产物分三层：决策页；按需求主题的分项设计；附录放事实依据、资产退场清单和确认记录。规格拆成子规范（存在 `umbrella.md`）时写一份总设计和每个子规范一份子设计，分工和位置见模板。

### 5. 收口并交给人工评审

初稿交付前统一核对以下四项；收到修改后，只复核受变化影响的部分：

1. **需求闭环**：规格、上级规范、项目规则和已确认决定里的每条权威要求都有落点：分项的“承接”、设计边界的硬约束或“不涉及的验收”；共同承接时写明各自部分。没有落点就补设计或列为待确认。
2. **理由闭环**：每个非显然的选择都写明理由和代价，核心决定写在决策页，其余写成紧跟机制的取舍卡；重点看模型的职责边界、接口的错误与兼容语义、图里的状态与事务安排。
3. **影响闭环**：涉及删除或替换资产时，按 `references/migration-strategies.md` 从退场对象做反向引用闭包，逐路径写进附录的退场清单。
4. **可读性闭环**：决策页不超过 1500 字；没有在两处定义的决定；没有只写“无”的按需字段；核对类表格第一列是被核对的对象；修订已直接改正文，没有追加段落。检查不过就改文档，不把问题留给评审者。

设计含高影响、难以靠当前上下文可靠自检的断言（例如不可逆数据迁移、退场资产可能仍被活代码依赖）时，运行时支持时加一次全新上下文、只读的独立评审：只给设计产物和权威依据清单，要求逐断言回到当前代码核实；它补充而不替代上述自检，简单或已有机械验证覆盖的设计不强制。

向用户讨论待确认项时，将前置条件已明确、彼此独立的决定同轮提出，最多三个且服从提问工具上限；依赖本轮答案的决定留到后续。用业务语言给出推荐、理由和主要后果，收到答案后改正文并在确认记录加一行。

返回文件路径或对话内设计，概括决定和风险，区分已有确认与新增待确认项；**实现前必须取得用户确认**，沉默不算批准。

### 6. 交接

- 用户确认后，把已确认的设计交给计划阶段或 `incremental-impl`；本技能不写实施步骤、切片顺序或代理分发。
- 重构在第一个结构性提交前，按 `test-driven-development` 建立行为保护证据。
- 未拆分的 `arch_design.md` 遵循仓库的临时规范生命周期：拉取请求就绪前晋升为稳定架构文档、归档到工作记录或删除，由 `documentation-management` 执行，不直接移动文件。长期有效的重大决策可另交该技能固化为架构决策记录。
- 拆分出的总设计和子设计随伞形文档保留；子规范全部上线后，在登记上线结果的拉取请求里把它的子设计压缩为已确认的决定、稳定文档或代码的链接、已知差异和验证结果链接；移走的内容先由 `documentation-management` 晋升到稳定文档、架构决策记录或局部指令，没有落点的不能删除。
