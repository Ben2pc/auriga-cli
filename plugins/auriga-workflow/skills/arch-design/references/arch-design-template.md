# `arch_design.md` 模板

存在实质性的架构、领域模型或跨边界决策时，将下面的模板复制到 `docs/specs/<topic>/arch_design.md`，并在实现开始前交给用户评审。

使用约定：

- 保留双语章节标题，正文使用对话语言。
- 删除写作提示、占位符和不适用的可选章节。
- 先写评审重点，再展示当前架构现状和当前目录结构，之后才写支撑细节。
- 当前与目标整体架构图保持同一抽象层级、相近布局和一致命名，让评审者直接看出改变前后；整体图优先采用 C4 模型的容器或组件语义，可用 Mermaid `flowchart` 表达以保证渲染兼容性。
- 新方案改变模块、组件或目录布局时，保留目标整体架构图和目标目录结构；没有改变的部分不重复展开。
- 细节图按评审问题选择：跨组件调用用 `sequenceDiagram`，生命周期与状态转换用 `stateDiagram-v2`，持久化数据关系用 `erDiagram`，重要领域类型关系用 `classDiagram`，数据流、部署拓扑和迁移路径用 `flowchart`。不为完整形式机械补图。
- 用户确认后更新评审状态；未确认前不进入实现。
- `Alternatives & Tradeoffs` 仅在存在真实取舍时保留本节，不为完整形式制造候选。

````markdown

> 用最短篇幅告诉评审者：本次改变什么、最需要确认什么、最大的风险是什么。

- **评审状态**：待人工评审 | 已确认
- **核心决定**：<需要确认的结构或领域决定>
- **主要影响**：<受影响的模块、调用方或数据>
- **技术质量重点**：<最需要确认的技术质量目标、预算、设计响应或代价>
- **首要风险**：<最值得质疑的假设或代价>
- **待确认项**：<尚未确定的代码映射、状态或边界；无则写“无”>

## Current Architecture / 当前架构现状

> 保留本节并展示设计前的整体结构。已有系统画当前模块、组件、外部依赖和关键依赖方向；全新系统明确写“当前无实现”，并画出将要接入的现有系统边界。整体图使用 C4 模型的容器或组件语义，并与后文目标图保持同一抽象层级。

```mermaid
flowchart LR
    CurrentA[当前模块或组件 A] --> CurrentB[当前模块或组件 B]
    CurrentB --> External[外部依赖]
```

## Domain Model / 领域模型

> 仅在涉及领域概念、职责、规则或状态变化时保留。不要把所有名词机械映射为类型，也不要把领域语义、设计变更和代码载体混在一个“概念”列里。先用模型清单回答“它是已有还是新增、是否对应具体代码”，再按概念说明领域语义。

### Model Inventory / 模型清单

> `变更状态` 只使用：已有保留、已有调整、本次新增、计划移除。已有代码实体必须沿用仓库标识符并给出仓库相对路径；本次新增代码实体必须给出设计标识符和预计路径；已有调整若改变标识符、载体或路径，在代码映射中同时写“现有：<映射> → 目标：<映射>”。没有独立代码载体时写“无独立代码实体（抽象概念）”，不要虚构类或文件；尚未决定时写“待确认：<具体问题>”，并把它列入人工评审重点。按适用形态填写，每个领域概念只保留一行，删除其余占位示例。

| `<已有调整的领域概念>` | 已有调整 | 现有：`<ExistingEntity>`（`<现有载体类型>`）— `<现有路径>` → 目标：`<TargetEntity>`（`<目标载体类型>`）— `<预计路径>` |
| `<新增且有代码载体的领域概念>` | 本次新增 | `<NewEntity>`（`<载体类型>`）— `<预计路径>` |

| `<映射待确认的领域概念>` | 本次新增 | 待确认：`<是否需要独立代码实体；若需要，确认载体类型、标识符和预计路径>` |
| `<计划移除的领域概念>` | 计划移除 | `<ExistingEntity>`（`<载体类型>`）— `<仓库相对路径>` |

### Concept Details / 概念说明

> 使用模型清单中的同一概念标识符，不在这里改名或重复代码路径。每个相关概念单独成节，删除不适用的字段，不把多条状态变化或规则压进表格单元格。
>
> “同一性判断”回答如何判断两个实例代表同一个领域对象，不是登录或认证身份：实体写持久标识，值对象写按值判等的字段，没有这类语义则写“无独立同一性”。“状态与存续范围”写何时产生、允许怎样变化、何时失效；可参考随聚合持久化、仅在单次事务内存在、仅在单次请求内存在等形态，这些只是示例，不是封闭枚举；没有状态变化时写“无状态”。`有效状态规则` 只写模型进入有效状态后仍必须成立的条件；输入校验、调用前提、授权策略和实现限制不属于这里，应分别放到公共契约、接口或约束章节。每条规则必须标明真实的成立边界，下面的边界示例同样不是封闭枚举；不为完整形式强行制造规则。

- **状态与存续范围**：<何时产生、允许的状态变化、何时失效；例如随聚合持久化、仅在单次事务或单次请求内存在> | 无状态

  - <必须成立的规则>（成立边界：<例如构造完成后、状态转换后、事务提交时或对外暴露时；按真实边界填写>）
````
