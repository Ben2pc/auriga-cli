# `arch_design.md` 模板

存在实质性的架构、领域模型或跨边界决策时，将下面的模板复制到 `docs/specs/<topic>/arch_design.md`，并在实现开始前交给用户评审。

使用约定：

- 保留双语章节标题，正文使用对话语言；删除写作提示、占位符和不适用的可选章节。
- 保留模板中的层级编号；新增同级需求或接口时只递增当前层级编号，并修复实际受影响的交叉引用，不因新增子节重排无关的后续一级章节。
- 按“总览 → 分项”组织：先让评审者看懂现状和目标全貌，再按需求主题逐项说明原始需求、设计、为什么以及验证方式。
- 一个分项可以聚合多条由同一设计机制承接的相关条款，但必须逐条列出来源；不要把每个细小验收断言机械拆成孤立章节。
- 当前和目标整体架构默认配图。只有单模块局部变化且图不能增加信息时才省略，并说明理由；两张整体图优先采用 C4 模型的容器或组件语义，保持同一抽象层级、相近布局和一致命名，让评审者直接看出改变前后。
- 图的第一语言是业务含义，代码标识用于准确锚定实现；不要画成只有类名、字段名或调用名的代码清单。
- 整体目录结构只在总览中完整展示一次；分项只补与该需求有关的局部新增或修改目录，避免重复整棵目录树。
- 模型按作用范围放置：跨多个分项复用、或负责维持跨分项规则的模型放在总览的 `Shared Model Design`；只服务当前分项的模型放在该分项的 `Local Model Design`。共享模型保留一张模型总表，分项直接展开模型详情；一个模型只定义一次，其他位置引用，局部模型扩大为跨分项模型时上移到总览。
- 细节图按评审问题选择：跨组件调用用 `sequenceDiagram`，生命周期与状态转换用 `stateDiagram-v2`，持久化数据关系用 `erDiagram`，重要领域类型关系用 `classDiagram`，数据流、部署拓扑和迁移路径用 `flowchart`。不按固定数量机械补图。
- 涉及接口时在承接该接口的分项中保留 `API Design`，紧邻对应需求列出输入、成功输出、错误输出和完整 DTO 形状。一个接口只在主要承接它的分项定义一次，其他分项引用，不另设全局接口章节。
- “为什么”不单独成节，直接写在它解释的模型、字段、接口、目录落点或图示旁边，让设计结论和理由一起接受评审。只有存在会显著改变成本、风险或行为保护方式的真实取舍时才比较候选；方向明确时直接写选择理由，不制造备选方案。
- 用户确认后更新评审状态；未确认前不进入实现。

##### 3.1.2.2 API Design / 接口设计

> 仅在当前分项新增或改变公共 API、服务端 API、模块接口、消息或命令契约时保留。一个接口只在主要承接它的分项定义一次，其他分项引用这里。每个接口说明使用方、设计理由和调用方真正依赖的契约；服务端 API 重点说明鉴权、权限、幂等、请求、响应和错误，模块接口重点说明调用前提、输入、输出和失败语义，消息或命令重点说明投递、重复消费、重放和失败语义。只保留当前接口形态真实适用的字段，不为填满模板制造语义。设计理由要解释接口为什么属于这个边界、隐藏什么实现以及关键形状为什么成立。
