# 组件与模块设计工具箱

## 何时使用

当设计需要划分组件、包、功能模块或构建目标，或者现有边界导致循环依赖、霰弹式修改、无关代码被迫一起发布时读取。局部类和函数整理不需要本资料。

## 可用兵器

- **共同闭包**：因同一原因、在同一时间变化的内容放在一起，减少一次需求跨越的模块数。
- **共同复用**：不会被一起使用的内容不要强行放进同一组件，避免调用方承担无关依赖。
- **复用与发布等价**：真正需要独立复用、版本化和发布的内容，才值得形成独立组件。
- **无环依赖**：组件依赖图保持无环；出现环时优先重新判断职责归属，再考虑依赖倒置或抽出共同能力。
- **稳定依赖**：易变部分依赖稳定部分，不让稳定核心反向依赖框架、界面或具体基础设施。
- **按功能与按能力组合**：上层通常按业务功能聚合，下层只把真正共享且稳定的能力独立出来。
- **删除测试**：假想删除中间模块并把实现放回调用方；复杂度若消失，它可能只是转手层，若在多处重复出现，它承担了真实封装。

## 选择提醒

- 早期项目优先让共同变化集中，成熟且被多方消费的组件才提高复用和发布独立性。
- 物理模块会增加构建、版本和协作成本；逻辑边界成立不等于必须立即拆成独立包。
- 移动端大型工程可以把编译时间作为真实驱动，但必须用现有构建数据说明收益。
- 不要为了套用原则同时引入接口、基础模块和协调模块；先选择能消除当前问题的最少结构。

## 输出到设计文档

在 `目标设计概览` 中展示目标组件全貌和依赖方向；在承接该变化的 `分项设计` 分项中解释职责为什么这样划分，并列出局部目录变化。只有存在独立发布或构建价值时，才写物理组件形态。
