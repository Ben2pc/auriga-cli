# 组件设计:内聚、耦合与移动端模块化

`arch-design` 主文档负责"切模块"的判断准则。这份参考补充**把模块组织成组件 / 包**这一层——出自《架构整洁之道》的组件原则,外加移动端大工程的模块化落地。在做组件划分(尤其工程已经是多组件的大工程)时读它。

## 组件内聚:一个类该放进哪个组件

三条原则,互相拉扯——它们一起回答"组件的边界画在哪"。

**复用/发布等价原则**
组件的粒度,就是复用的粒度,也是发布的粒度。能被一起复用、需要一起发布的东西,放进同一个组件。一个组件里的内容应该对同一群使用者有意义。

**共同闭包原则**
会因为同样的原因、在同样的时间一起变的类,放进同一个组件。这是组件层面的"沿变化轴切"——和主文档 B1 的准则同源,只是从模块抬到了组件。一个改动最好只波及一个组件。

**共同复用原则**
不会被一起复用的类,不要塞进同一个组件。否则调用方为了用其中一个,被迫依赖上它根本不用的另一个——它那一侧每次发布,调用方都被动跟着升级、重测。

## 三条原则的张力,怎么权衡

这三条会互相拽:

- 偏向"复用等价"和"共同闭包" → 组件做大 → 一点小改动就触发整个大组件发布,使用者被不必要地频繁惊动。
- 偏向"共同复用" → 组件做小、做专 → 一个功能改动要同时发布一串小组件,协调成本高。

没有一劳永逸的切法,跟项目阶段走:

- **早期 / 快速演进**:偏"共同闭包"——优先可开发性。组件粗一点,让改动集中、好定位。这时复用还不是真问题。
- **成熟 / 被多方依赖**:偏"复用等价 + 共同复用"——优先可复用性和稳定性。把被多处复用的部分抽细、抽稳。

组件划分是会随项目演进重新调整的,不要追求一次到位。

## 组件耦合:组件之间怎么连

**无环依赖原则**
组件依赖图里不能有环。环会让一组组件焊死成一块——没法独立构建、独立测试、独立发布。出现环,两种打破方式:在环上某条边做依赖倒置(加一个接口,把依赖方向反过来),或抽出一个新组件把共同依赖的东西收进去。

**稳定依赖原则**
依赖应该指向更稳定的方向。一个组件的"稳定性"看它被多少东西依赖——被依赖得越多越稳定,因为改它的代价越大。不稳定、easy-to-change 的组件,不该被稳定的组件依赖上;否则那个本该易变的组件被钉死了。

**稳定抽象原则**
稳定的组件应该是抽象的。一个组件如果又稳定(改它代价大)又具体(实现细节多),它就僵化了——想改改不动。所以:稳定的组件靠抽象(接口、策略)来保持"虽然稳定但仍可扩展";不稳定的组件可以是具体的。稳定度和抽象度应该正相关。

> 这三条耦合原则,加上主文档的依赖规则,本质都在说同一件事:**让依赖指向稳定和抽象,不要让稳定的东西被易变的东西拖住。**

## 移动端大工程的模块化落地

移动端工程通常很大、组件很多,上面的原则要落到具体的模块边界上:

**按 feature 切,还是按能力切**
- 按 feature 切(一个功能一个模块)对应"共同闭包"——一个功能一起变。
- 按能力切(网络、持久化、UI 基础库)对应"复用等价"——被多个 feature 复用。
- 大工程一般两者都有:**底座是按能力切的基础设施组件,上层是按 feature 切的功能组件**。

**依赖方向**
- feature 模块依赖基础设施模块,不反过来——基础设施更稳定,符合稳定依赖原则。
- feature 模块之间不直接互相依赖。需要交互,靠更上层的协调模块,或事件 / 路由这类间接机制。否则 feature 之间织成网,无环依赖原则就破了。

**编译时间是一个真实的设计驱动**
模块边界也是增量编译的边界——改一个叶子模块,只重编它和它的依赖方。在移动端,编译时间通常值得作为一个明确的设计驱动列进权衡(对应主文档「设计驱动词汇表」里的"性能",此处指开发时的构建性能)。这是少数几个"为未来"花成本却站得住的地方,因为它有可度量的当下收益。

**模块的物理形态**
iOS 上常见的承载形式:Swift Package(源码或二进制)、framework、app 内的 feature target。选哪种是工程选择,不影响上面的逻辑边界——逻辑边界先定,物理形态后选。

## 关于 SOLID 的一句说明

主文档里的依赖规则、抽象规则、窄接口 / 信息隐藏、沿变化轴切模块,加上这份参考里的组件内聚与耦合原则,合起来就是业界常说的 SOLID 原则与组件原则。这个 skill 按**可操作的说法**把它们拆开讲——命名行为,而不是背字母缩写。所以你不会在文档里看到一个叫"SOLID"的小节;它一条不少,只是没以教科书清单的形式出现。(SOLID 里的"里氏替换"偏类型与继承,是代码层面的事,不在这个架构 skill 的范围内。)
