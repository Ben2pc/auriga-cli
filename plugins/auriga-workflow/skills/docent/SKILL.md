# Docent：代码讲解员

Agent 写代码的速度远超人类阅读代码的速度，人类对代码库的心智模型持续落后。docent 把"理解 xx 的代码逻辑"从线性的对话问答升级为一份可视化、可交互、可离线打开的理解制品。

**核心目的**：让一个没跟上进度的人类，在约 10 分钟内建立对目标代码逻辑的**正确**心智模型。报告的一切形式选择都服务于这个目的。

## 何时使用

- 仅当用户显式调用 `/docent <参数>` 时使用。**不要**在普通问答（"这个函数返回什么"）中自动触发本 skill——那种问题直接回答即可。

## 入口

`/docent <自然语言问题 | 路径>`

| 参数形态 | 处理方式 |
|---|---|
| 仓库内存在的文件或目录路径 | 理解范围即该路径，跳过定位阶段 |
| 其他文本 | 当作主题（例："用户登录后 token 是怎么刷新的"），由子代理先定位相关代码 |
| 无参数 | 先问用户想理解什么（`AskUserQuestion` / `request_user_input`），不要凭空猜测范围 |

## 执行模型：单个专职子代理

主 agent 只做三件事：解析参数、派遣**一个**专职子代理、交付结果。定位→通读→合成→生成的全过程都发生在子代理内部。

为什么是一个而不是多个：理解是不可分割的认知过程——"A 文件里这个判断为什么存在"的答案往往在 B 文件里。并行碎片化阅读会切断跨文件因果链，拼装出"每个文件是什么"，拼不出"它们为什么这样咬合"。子代理的价值不在并行，而在**隔离**：把批量代码阅读的上下文消耗挡在主对话之外。

派遣时把以下内容完整交给子代理：用户的原始问题或路径、当前工作目录、本 skill 所在目录的绝对路径（下称 `<skill-dir>`，子代理需要自读 `<skill-dir>/references/design-guidelines.md`）、当次对话语言。若当前运行时不支持派遣子代理，可以在主对话内完成同一流程，但要在交付时提醒用户本次会话上下文已被大量代码阅读占用。

## 子代理工作流

### 1. 定位（路径入口跳过本阶段）

从多个角度找相关代码，避免单一搜索姿势漏掉东西：

- 按文件名 / 目录名搜索主题关键词
- 按符号名（函数、类、配置键）搜索
- 按字符串字面量（报错文案、日志、用户可见文案）搜索
- 按 git 历史搜索（`git log -S` / `--grep`，看最近谁改过相关文件）

汇合成两份清单：**核心文件**（将通读）与**外围文件**（仅记录关联，不深入）。范围过大装不下时，宁可缩小核心清单也不要降低阅读质量——裁剪必须在报告"阅读足迹"一节可见。

### 2. 通读

按逻辑流（而不是文件顺序）通读核心文件：从入口开始，沿调用链和数据流走。读的过程中持续回答"它为什么这样咬合"，不只是"它是什么"。对照 git 历史理解关键演化节点。

### 3. 合成：必答九条

一份合格的报告必须回答以下九个问题。范围很窄时（如单个小文件），个别维度允许**显式标注"不适用"**，但禁止静默缺失：

1. **为什么存在**——这段逻辑解决什么问题
2. **入口与主流程**——入口在哪、主流程怎么走
3. **代码地图**——把涉及的文件放在目录结构里讲：相关代码在仓库中的位置布局，每个文件标注它扮演的角色。带着结构讲定位，不要把"哪些文件"和"在哪里"拆成两节
4. **数据流转**——关键数据 / 状态如何流转
5. **坑与特例**——有哪些不明显的约束、坑、边界特例
6. **相邻契约**——对外承诺了什么、依赖谁、谁依赖它；改动它的影响面
7. **历史演化**——从 git 历史看它为什么长成现在这样（关键提交的动机）
8. **如何验证理解**——读者怎么亲手确认报告讲的行为：哪个测试覆盖了它、怎么跑一次看到行为
9. **阅读足迹**——读了哪些文件、为什么认为相关、哪些可能相关但未深入（含范围裁剪说明）。这一节是读者发现"你漏看了 X"的依据

### 4. 生成 HTML 报告

**不固定模板**——呈现形式由你针对当次问题自行设计。先读两份参考：`<skill-dir>/references/design-guidelines.md`（设计规范）和 `<skill-dir>/references/components.md`（组件库使用指南）。

**拼装纪律**：最终 HTML 由 `<skill-dir>/scripts/assemble.sh` 拼装产出（固定资产 `assets/tokens.css`、`assets/components.css`、`assets/renderers.js` 由脚本注入，渲染器定义在 `<head>`，正文内联脚本可直接调用）。你只生成三样并交给脚本：正文片段、图的 JSON 数据（写在正文内联脚本里）、当次定制的版式 CSS。严禁通过模型逐字重打资产内容；画图写 JSON 调渲染器，不要手画 SVG 坐标；版式、叙事、设计立场仍然每次定制。用法与数据契约见 components.md。

可视化手段调色板（按问题自选，不要全用）：

- 时序图——讲一次请求 / 调用链路
- 流程图——讲分支决策逻辑
- 状态图——讲状态机
- 对照表——讲配置优先级、多实现差异
- 可折叠的多层级下钻——概览到细节的渐进披露
- 带锚点的代码片段——关键代码原文 + 讲解

**硬性质量约束**（违反任何一条即不合格）：

- **第一屏架构总览**：报告开篇在一句话结论之后，先给一张**架构总览图**——涉及的模块 / 文件和它们的关系（"代码地图"的图形化呈现），让读者先建立空间感，再进流程细节
- **主流程图**：报告**至少一张**标准软件工程图（时序图 / 流程图 / 状态图，按问题选型）承载"入口与主流程"，节点带锚点。图是人类读逻辑的通用语言，纯文字叙述不能替代。范围极窄时架构总览与主流程图允许合并为一张
- **锚点**：所有关于代码的结论附 `文件:行号` 锚点，可追溯到仓库具体位置
- **自包含离线**：单文件 HTML，打开时零网络请求。图表用内联 SVG 或纯 HTML/CSS 绘制，不引入需要从网络加载的脚本库；字体用系统字体栈或内联资源
- **阅读足迹**：必答第 9 条不可省略，这是用户纠偏的依据
- **语言**：报告正文跟随当次对话语言（代码标识符与锚点除外）
- **落点**：写入 `/tmp`（如 `/tmp/docent-<主题slug>.html`），不落进项目仓库

## 交付

子代理返回后，主 agent：

1. 自动用浏览器打开报告（macOS 用 `open <文件>`，其他平台用对应命令）
2. 在主对话给出：报告文件路径 + 一段文字摘要（讲了什么逻辑、读了哪些核心文件、有什么值得注意的发现）

## 纠偏循环

"阅读足迹"一节的存在意义是让用户能发现定位偏差。用户指出"漏看了 X"或"方向不对"后：在同一会话内重新派遣子代理修订（把用户反馈和上一份报告路径一并交给它），产出更新的报告。不引入任何跨会话持久化状态。

## Must Not

- Must not 并行派遣多个子代理分头阅读——碎片化阅读切断因果链
- Must not 把报告或中间产物写进项目仓库
- Must not 复用固定 HTML 模板——每份报告按问题定制设计
- Must not 在报告里写没有锚点支撑的代码结论
- Must not 静默裁剪范围——所有"没读 / 没深入"都要在阅读足迹一节可见
