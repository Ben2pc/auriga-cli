# 接口设计手册

`arch-design` 主文档的「接口设计」那节给的是**架构高度**的四条原则——它们决定接缝画在哪、契约长什么形状。这份参考是接口**落地**时的实现手册:契约定下来之后,接口怎么真的写出来才不会坑到调用方。

设计接缝、定接口契约时读它的前半(根本心法、演进);接口真要实现时读它的后半(错误语义、校验、REST、命名、类型)。这些是跨语言、跨项目稳定的实践——**先跟随项目已有约定**,代码库里已有的写法优先于这份手册。

## 根本心法:可观察即契约(Hyrum 定律)

> 一个接口只要用的人足够多,它**所有**可观察的行为都会被某个调用方依赖上——不管你的文档怎么承诺。

这是接口设计所有规则的根:你以为没承诺的东西(字段顺序、错误信息的措辞、一个恰好为空的返回、响应慢到某个程度才超时),只要露出去,就有人依赖。推论:

- **接口越窄越好。** 暴露的每一样东西都是一份你没打算签、但已经签了的契约。只暴露调用方真正需要的,藏住其余的——这就是主文档「窄接口 / 信息隐藏」。
- **契约先行。** 接缝的接口在设计阶段就定形,不要边写实现边让它长出来。实现可以改,定下来并暴露出去的契约改起来要付全体调用方的代价。
- **泄漏出去的就收不回来。** 一旦某个可观察行为被依赖,删掉它就是破坏性变更——哪怕文档从没承诺过它。

## 错误语义

错误是接口契约的一部分,而且是最容易被忽视、又最容易不一致的那部分。

- **结构化的错误体,全站一致。** 所有错误返回同一个形状,不要这个端点返回字符串、那个端点返回 `{msg}`、另一个抛裸异常。
- **机读的 code + 人读的 message 分开。** `code` 给程序分支用,稳定、可枚举(`USER_NOT_FOUND`);`message` 给人看,可以改措辞。调用方分支判断只认 `code`,绝不靠匹配 `message` 文本。
- **和传输层状态码对齐。** HTTP:4xx 是调用方的错(别用 200 包一个错误体——那等于逼调用方去解析 body 才知道成没成),5xx 是服务端的错。语言内的接口:错误用哪个通道(异常 / `Result` / 错误码)要和模块其余部分一致。

```jsonc
// 一致的错误体形状
{
  "error": {
    "code": "USER_NOT_FOUND",        // 机读、稳定、可枚举
    "message": "找不到该用户",        // 人读、措辞可改
    "details": { "userId": "..." }   // 可选,定位用
  }
}
```

## 边界校验

**只在系统边界校验输入,不在内部代码到处校验。** 边界是:API handler、表单提交入口、外部服务响应的接收点、读文件 / 读环境变量的地方。

- 边界**之内**,数据应当已经可信——内部函数不必反复 `if (x == null)`。到处防御性校验会把代码淹没在噪声里,而且掩盖"这个值到底该不该可能为空"。
- 边界**之上**,校验要严:类型、范围、必填、格式。外部输入在跨过边界**之前**不可信。
- 校验失败 → 用上面的错误语义返回,不要让坏数据漏进系统再在深处炸。

这条和主文档的依赖规则一脉相承:把"不可信"挡在边界外圈,核心逻辑活在干净的内圈。

## REST 资源设计

做 HTTP 接口时的成形约定(GraphQL 另有一套,但"资源/契约先行/演进"的心法相通):

- **资源用复数名词,不带动词。** `GET /users`、`GET /users/{id}`,不是 `/getUser`、`/createUser`。动作由 HTTP 方法表达。
- **列表端点要分页。** 永远假设列表会变长。提供页大小和排序参数,定义好默认值。不分页的列表端点是一颗定时炸弹。
- **过滤用 query 参数。** `GET /users?status=active&role=admin`。
- **局部更新用 PATCH,不用 PUT。** PATCH 只动传来的字段,没传的保持不变;PUT 语义是整体替换,漏传字段会被清空。
- **端点结构可预测。** 同一套命名和层级规律贯穿所有资源,让调用方能猜对没读过文档的端点。

## 演进与向后兼容

接口一定会变。变的方式决定影响半径(主文档的设计驱动之一)。

- **加,不要改或删。** 新增可选字段、新增端点——老调用方不受影响。改签名、删字段、改字段含义、收窄返回类型——全是破坏性变更。
- **为扩展设计,不为修改设计。** 留好"以后能加东西"的形状(比如返回一个对象而不是裸值,这样以后能加字段)。注意这不等于主文档反对的"夸夸其谈通用性"——区别在于:留扩展形状几乎零成本,堆推测性抽象有持续成本。
- **新可选字段要有安全的默认。** 老调用方不传它时,行为必须和加这个字段之前一致。
- **真要做破坏性变更**,走主文档「迁移形态」的「并行变更」:新老接口并存 → 调用方逐个迁 → 删老接口。

## 命名规范

命名是接口契约里最便宜、又最常被随手破坏一致性的部分。

- **字段 / 参数**:同一套大小写风格贯穿全接口(JSON 接口通常 `camelCase`)。
- **枚举值**:`UPPER_SNAKE_CASE`,稳定、可枚举。
- **布尔**:`is` / `has` / `can` 前缀(`isActive`、`hasPermission`、`canEdit`)——一眼看出是布尔,也避免 `active` 这种既像名词又像形容词的歧义。
- **别用误导性的名字**:名叫 `getX` 的接口不该有副作用;名叫 `list` 的不该只返回一个。

## TypeScript 类型模式

类型系统能把一部分接口契约变成编译期就拦得住的东西。

**可辨识联合**——表达"几选一"的变体,让编译器强制每个分支都处理:

```typescript
type Result =
  | { status: 'ok'; data: User }
  | { status: 'error'; code: string };
// 用的时候按 status 收窄,漏处理一个分支编译器会报
```

**输入 / 输出类型分离**——调用方提供的数据和服务端生成的数据,是两个类型,不要共用一个:

```typescript
type CreateUserInput = { name: string; email: string };
type User = CreateUserInput & { id: string; createdAt: string };
// id / createdAt 由服务端生成,调用方不该、也不能传
```

**branded 类型**——给本质不同、底层却都是 `string` 的 ID 各自一个类型,防止串用:

```typescript
type UserId = string & { readonly __brand: 'UserId' };
type OrderId = string & { readonly __brand: 'OrderId' };
// 把 OrderId 传进要 UserId 的地方,编译期就报错
```

## One-Version 规则

同一个依赖、同一套接口,**在一个系统里只允许存在一个版本**。同时存在多版本会引发"钻石依赖":模块 A 要某依赖的 v1,模块 B 要 v2,它们汇到一起就冲突。这本质是依赖图的问题,和主文档的「无环依赖」「依赖方向」同属一个世界——多版本并存让依赖图既有环又有歧义。

要升级一个被广泛依赖的接口,用「并行变更」整体迁移,而不是让新老版本长期共存。

## 常见自我辩解

| 自我辩解 | 实情 |
|---|---|
| "这个字段没写进文档,改它不算破坏" | Hyrum 定律:没写进文档但可观察,一样有人依赖。改它就是破坏性变更。 |
| "先把接口实现出来,形状自然会清楚" | 契约边写边长,会长成实现的形状,而不是调用方需要的形状。契约先行。 |
| "校验放函数里更保险" | 内部到处校验是噪声,还掩盖"这个值到底该不该为空"。校验归边界。 |
| "返回 200 带个错误标志更简单" | 那逼每个调用方解析 body 才知道成没成。状态码就是给这个用的。 |
| "ID 都是字符串,一个 string 就够了" | 不同 ID 串用是真实的线上事故来源。branded 类型让编译器拦住它。 |

## 接口验收清单

- [ ] 接口只暴露调用方真正需要的——没有顺手露出去的实现细节。
- [ ] 错误体形状全站一致;机读 `code` 和人读 `message` 分开;状态码对齐。
- [ ] 输入校验只在边界做;边界之内的数据可信。
- [ ] 列表端点有分页;局部更新用 PATCH。
- [ ] 命名风格一致(大小写、布尔前缀、枚举);没有误导性的名字。
- [ ] 这次接口变更是"加"——没有改签名 / 删字段 / 改含义;新可选字段有安全默认。
- [ ] 没有引入同一依赖的第二个版本。
