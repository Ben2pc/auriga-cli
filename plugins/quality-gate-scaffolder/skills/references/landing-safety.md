# 落地安全

质量门禁可能阻塞所有贡献者。即使第一版实现很小，也要把脚手架当成生产基础设施对待。

## confirmation-before-write

编辑目标仓库前，先向用户展示拟新增或修改的文件与远端设置，并要求明确批准。方案必须点名：

- 新增或修改的文件；
- 会在本地运行的命令；
- GitHub Actions 工作流名和必需检查名；
- 分支 ruleset 或 branch protection 变更；
- 已知风险，例如检查过慢或误报。

不要从沉默推断同意。

## 写入纪律

拿到批准后：

- 从最窄但有用的脚手架开始；
- 把项目专属规则保留在目标仓库里；
- 优先复用已有包管理脚本和辅助函数约定，而不是新增包装层；
- 当目标技术栈有合适测试运行器时，为门禁规划器、解析器和配置守卫加测试；
- 在声称可以使用前，先在本地运行新的门禁入口。

## 远端设置

会改变合并行为的远端 GitHub 写操作，需要第二次明确确认。这包括创建或编辑：

- ruleset；
- branch protection；
- required status check；
- code owner review 要求；
- required conversation resolution。

如果无法修改远端设置，输出精确的手工设置步骤，并说明哪些部分尚未验证。
