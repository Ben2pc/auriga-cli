# 三层质量门禁模型

每一次搭建门禁都使用这个模型。方案和实现都要把三层分开，后续 Agent 才能单独调整某一层，而不需要猜测某条规则到底属于哪里。

## 第一层：检查工具

检查工具是可以执行的机制：

- 包管理脚本，例如 `npm run lint` 或 `pytest`；
- 原生构建工具，例如 `xcodebuild`、Gradle 或 `swift test`；
- 静态检查和分析工具，例如 SwiftLint、Detekt、Ruff、Mypy、Biome、ESLint、TypeScript、Import Linter 或 Android Lint；
- 项目自有编排入口，例如 `tools/quality/run_gates.sh`。

能收敛到一个稳定入口时，优先为每个技术栈保留一个入口。这个入口内部可以调用很多工具，但用户和 GitHub 必需检查不应该记住内部工具清单。

工具选型要基于目标仓库已经存在的工程现实，而不是另起一套“理想工具链”。输出时说清楚每个工具负责什么、不负责什么，以及版本怎么选：固定到锁文件、使用补丁线约束、跟随构建工具链，还是只在专门升级 PR 中显式提升。

## 第二层：检查规则

检查规则是工具实际执行的项目策略：

- 格式化和 lint 风格；
- 模块边界或导入边界；
- 本地化、资源和设计 token 契约；
- 测试隔离、测试夹具和默认无网络约束；
- 生成文件漂移、依赖约束或部署不变量。

规则应当放在版本化的仓库文件里。如果一条规则只存在于对话、工单或私有文档里，它还不是硬门禁。

## 第三层：调用时机

调用时机决定工具什么时候运行：

- 本地 git hook，用来给开发者快速反馈；
- GitHub Actions 的拉取请求工作流，用来做共享强制执行；
- 定时工作流，用来跑昂贵回归；
- 分支 ruleset 或 branch protection，用来设置必需检查和审查规则；
- 自动审查系统能创建未解决线程时，用阻塞式审查评论承载高层问题。

本地 hook 是便利层，持续集成才是权威层。任何必须阻止合并的规则，都应该进入必需检查或 ruleset，而不能只存在于开发者本机 hook。

## 期望输出

使用这个模型时，输出方案需要包含：

- 第一层工具表：命令、用途、预期耗时、版本选择策略；
- 第二层规则表：规则来源文件、当前规则摘要、失败形态；
- 第三层调用时机表：本地 hook、GitHub Actions 任务名、必需检查名、ruleset 设置、是否基于 diff，以及动作属于本地还是远端；
- 脚本和 workflow 示例：至少覆盖本地 hook、拉取请求持续集成、合入 `main` 后或定时检查中的一种；
- 一小段待用户确认的未决决策。
