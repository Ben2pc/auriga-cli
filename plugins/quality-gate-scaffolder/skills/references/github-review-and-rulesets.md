# GitHub 审查和 Ruleset

硬门禁需要仓库侧强制执行。GitHub 设置是合并权威，本地检查只负责快速反馈。

## 拉取请求检查

使用稳定的必需检查名。如果一个工作流里有多个任务，先确认拉取请求状态列表里实际出现的任务名，再加入必需检查。

可以考虑的检查：

- 技术栈专属门禁任务，例如 `Quality Gates`、`Backend Gates` 或 `Frontend Gates`；
- 门禁脚本自身的测试任务，例如 `Quality Script Tests`；
- 当自动审查是仓库策略的一部分时，使用能创建阻塞式行内线程的代码审查任务。

## Ruleset 设置

对受保护默认分支，可以考虑：

- 禁止删除和非快进推送；
- 合并前必须经过拉取请求；
- 当存在 `CODEOWNERS` 时要求 code owner review；
- 要求 conversation resolution；
- 要求技术栈门禁状态检查；
- 如果仓库已有这个约定，使用 squash-only merge。

不要因为来源项目使用了某条规则，就直接在目标仓库启用它。先确认目标仓库拥有相同的贡献者模型、分支策略和检查名。

## 自动审查线程

如果仓库把自动审查当作硬门禁，优先使用能为阻塞问题创建未解决行内线程的系统。再配合 required conversation resolution，让合并按钮能反映审查结果。

这个插件参考的来源项目采用了这种模式：持续集成承载确定性的工具结果，阻塞式审查评论承载无法完全用静态检查表达的高层问题。
