# ADR-002: 将 systematic-debugging 内化到 auriga-workflow

## 状态

已接受，取代 ADR-001。

## 日期

2026-07-14

## 背景

ADR-001 选择继续使用 `obra/superpowers` 的外部技能，并约定在模型能力显著变化时重新评估。面向 GPT 5.6 Sol 与 Fable 5 的本轮评审发现，旧技能的证据优先原则仍有价值，但固定四阶段、绝对化停止规则和级联技能调用会重复新模型的原生能力，也无法妥善覆盖低频线上问题和需要先恢复服务的生产事故。

Auriga 已经通过 `auriga-workflow` 插件发布双运行时自有技能，并具备清理旧独立技能副本的迁移机制。继续把核心调试契约留在外部锁文件中，会让行为和升级节奏受上游控制。

## 决策

保留 `systematic-debugging` 名称，将其作为 `auriga-workflow` 插件的自有技能发布，不再通过 `skills-lock.json` 和外部技能安装器分发。

新契约保留证据优先和根因判断，同时改为自适应流程：优先建立可重复的问题验证路径；无法立即复现时建立线上证据采集路径；最小复现与常见诊断方法按需选择；线上事故允许先执行可逆的临时缓解，但不得把缓解描述为根因修复。

## 考虑过的备选方案

### 继续使用 obra/superpowers

- 优点：无需维护本地正文，可以继续接收上游更新。
- 缺点：核心工作流行为不受 Auriga 控制，固定流程与新模型能力不匹配。
- 否决原因：本轮升级的目标就是降低过度约束，同时覆盖线上证据采集和事故止损；上游当前契约无法满足。

### 直接采用 mattpocock/skills diagnosing-bugs

- 优点：强调可执行的问题验证路径，诊断工具更贴近现代代理能力。
- 缺点：仍强制最小化、固定数量假设和用户检查点，不能作为更轻的直接替代。
- 否决原因：适合作为方法来源，不适合作为 Auriga 的完整行为契约。

### 同时保留外部与自有版本

- 优点：迁移期间表面兼容。
- 缺点：同名或相近触发会产生重复加载和行为冲突。
- 否决原因：插件安装已经能清理旧独立副本，没有长期并存的必要。

## 后果

- Auriga 可以独立调整调试技能，以适配不同模型和运行时。
- 预设安装减少一个外部技能下载，`systematic-debugging` 改由插件提供。
- 安装或升级 `auriga-workflow` 时会清理项目级或用户级的旧独立副本，防止其遮蔽插件版本。
- 后续有价值的上游方法需要人工评审后吸收，不再自动随上游变化。
- 技能正文、插件清单、双语说明和迁移测试成为同一维护责任的一部分。
