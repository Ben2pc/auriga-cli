# Spec Design Modernization — Spec（需求规格技能现代化 — 规范）

> 先判断需求是否值得做，再通过基于事实的苏格拉底式提问与用户对齐目标，避免长程执行数小时后才发现方向错误。

## Why (为什么做)

AI 已显著降低代码生产成本，但没有同步降低产品复杂度、维护负担、用户认知成本、运行风险和机会成本。Agent 如果把用户带来的每个想法都直接加工成实现规格，会高效地建设并不值得做的功能；如果只凭主观感觉判断需求已经明确，又可能在错误目标上长程运行数小时后才暴露分歧。

`spec-design` 仍有不可替代的职责：调查当前事实，帮助人类判断需求价值，暴露隐含假设与相互依赖的产品决定，并把共同理解固化成可供架构设计、实现和评审消费的行为契约。它需要吸收 Matt Pocock `grilling` 的有效内核，但不继承无限追问、无持久产物或把所有任务都流程化的缺点。

## Findings (调研发现)

- 当前 `plugins/auriga-workflow/skills/spec-design/SKILL.md` 强制使用 `Q+GUESS`、约 95% 置信度、最多约十轮、六行复述、2–3 个候选方案和逐章节确认；这些规则把需求是否明确交给模型的主观置信度，并增加固定交互成本。
- 当前技能默认把输入转换成 `spec.md` 与 `validation-contract.md`，但 `deep-review` 的 `spec-conformance` 已明确承认当前对话中的一句话要求也可以是权威规格。
- 当前 `validation-contract.md` 模板同时承载验收断言和仓库具体工具链，后者会与 `test-driven-development`、`docs/rules/test/` 对测试设施的调查职责重复。
- 当前拆分规则使用 VAL 数量、模块数、子系统数、界面组件数和代码行数等固定阈值，并混入抽象分支等实施策略，未完全按独立用户结果拆分需求。
- Matt Pocock 最新 `grilling` 技能的核心是沿决策树一次解决一个决定、每题给出推荐答案、能从环境调查的事实不询问用户、决定由人确认，并在共同理解确认前禁止行动。
- `grilling` 的社区反馈显示它能提前暴露遗漏和错误假设，但也存在数小时或上百个问题、进度不明、会话结束后决定丢失，以及部分运行时越过停止门禁直接实现的问题。
- 当前仓库不存在适用于本任务的 `docs/rules/spec/`，无项目专属 spec 规则。

## What (做什么)

### 1. 先经过有界的价值门禁

Agent 在展开完整需求澄清前，先调查当前可获得的用户反馈、使用数据、现有行为、故障记录、替代流程和相关项目事实，再帮助用户判断需求是否值得投入。

价值门禁默认只问一个问题，确有必要时追加第二个，最多两轮。每个问题同时给出已知事实、需要人决定的判断、Agent 的推荐答案与理由，以及成本更低的替代思路。用户可以随时直接选择出口，不必完成全部提问。

价值门禁必须落到一个明确出口：

- **值得做**：进入需求事实调查与目标对齐。
- **先验证**：定义单一价值假设、最低成本实验、继续信号和停止信号，不直接建设完整功能。
- **暂缓**：记录重新评估所需的证据或条件后停止。
- **不做**：停止规格和实现，不为完成流程制造产物。

安全、合规、严重故障和数据正确性等必做事项可以简化价值讨论，但仍要确认风险、影响和优先级。两轮后证据仍不足时，推荐“先验证”或“暂缓”，不能继续无限讨论，也不能默认进入完整实现。

### 2. 用调查事实建立需求上下文

需求是否明确不能依赖模型记忆、置信度或主观印象。Agent 应读取与任务相关的代码、现有行为、接口、测试、项目规则、产品资料、用户提供的原型和外部来源；事实来源按相关性选择，不把 `AGENTS.md`、README 或任一单一文档视为所有场景的唯一事实源。

能够从环境中查明的事实由 Agent 自行调查。事实冲突或无法获得时，明确记录证据缺口；只有事实无法决定的目标、范围、产品语义和取舍才交给用户。

Figma、网页或外部文档在当前运行时有可用工具时直接读取；无法访问时再请求截图、导出文件或关键内容，不写死某个运行时必然无法访问。

### 3. 通过苏格拉底式提问对齐目标

需求澄清不是收集表单答案，而是帮助用户检验需求价值、暴露未经验证的假设，并确认答案之间与原始目标保持一致。

Agent 根据调查事实建立会改变最终用户结果的决策树，沿依赖关系一次解决一个决定。每个问题应说明触发它的事实、推荐答案及其主要后果；推荐用于降低沟通成本，不替用户批准产品决定。没有真实决策分支时不制造候选或问题。

需求对齐至少明确目标用户与问题、期望结果、范围与范围之外、用户可观察行为、成功信号以及仍存在的证据缺口。若两个独立且称职的 Agent 仍能依据当前要求产生明显不同的用户结果，并都合理声称满足需求，则澄清尚未完成。

停止条件不是固定问题数或主观置信度，而是剩余未知项已经不会实质改变需求价值、目标、用户可观察行为、范围或验收契约。剩余的系统结构决定交给 `arch-design`，实施步骤、切片、顺序和分发交给计划阶段。

### 4. 让确认结果成为权威规格

用户必须明确确认双方已经形成共同理解，Agent 才能进入架构设计、计划或实现。实现开始后若发现新的产品歧义，应返回需求澄清并更新权威决定，不能为了维护既有草稿而禁止重新打开规格。

快速开发流程中，范围清楚、无需跨会话或跨 Agent 交接的一句话需求，可以由当前对话中的用户确认作为权威规格，不强制生成文件。出现以下任一情况时，默认写入 `docs/specs/<topic>/spec.md` 与 `validation-contract.md`：

- 需求包含多个用户可观察结果或需要逐项追溯验收；
- 涉及公共接口、共享契约、跨模块行为或实质范围取舍；
- 需要跨会话、跨 Agent 或交给独立评审者消费；
- 工作会跨多个提交或拉取请求；
- 用户明确要求保存规格。

文件化规格只保存确认后的价值判断、行为和决定，不记录冗长问答流水。`spec.md` 的 Why 应能说明谁遇到什么问题、证据是什么、为什么值得现在解决、预期改善什么，以及为什么不采用不做或更小替代方案。

### 5. 保留精简的验收契约

`validation-contract.md` 继续作为测试驱动开发和需求符合性评审的承重产物。每条 VAL 表示一项需要证明的验收断言，不等于单个测试用例；实现阶段可以按风险展开为多个用例。

每条 VAL 只保留中文的“验收要求、验证方式、通过标准”，但不规定具体测试运行器、驱动、测试函数、模拟方式或代码组织。编号分类使用完整英文语义词并配中文短标题，避免项目自造缩写增加人工审查成本。删除强制的仓库具体工具链表；具体测试设施由 `test-driven-development` 结合 `docs/rules/test/` 和现有测试调查确定。

### 6. 按独立用户结果拆分大需求

删除固定 VAL 数、模块数、子系统数、界面组件数和代码行数门槛，也不在需求阶段指定抽象分支等实施策略。只有当一个需求可以形成独立确认、独立验收且不误导总体目标的完整用户结果时，才拆成子规范。

跨多个拉取请求的总规范继续放在 `docs/long-running-specs/`，保留共同目标、约束、父子 VAL 覆盖关系和状态；每个子拉取请求仍使用自己的 `docs/specs/<child-topic>/` 契约。长期规范不能绕过子拉取请求的人工确认和 Ready 生命周期。

### 7. 精简主文件和模板

删除固定置信度、固定轮数的需求追问、六行复述、强制多候选、逐章节确认、Playground 与静态网页审查入口，以及为完整形式保留“无”的可选章节。主文件只保留价值门禁、事实调查、目标对齐、产物选择、确认门禁和交接边界；确切文件形态保留在按需读取的模板中。

## Out of scope (本次不做)

- 不把 Matt Pocock 的 `grilling` 或 `grill-with-docs` 作为新的运行时依赖安装。
- 不在需求规格中定义领域模型、模块边界、接口实现、数据流或技术质量目标。
- 不在需求拆分阶段规定实施单元、提交边界、Agent 分发或迁移手法。
- 不要求所有需求提供精确收入、成本或投入回报数字。
- 不执行 GPT 5.6 Sol 或 Fable 5 的模型行为评测；本轮依据当前协议职责、社区反馈和技能文本完成精简。
