# incremental-impl 评审

## 当前职责

`incremental-impl` 消费已经确认的需求、架构设计和计划，把非平凡需求改动拆成完整、可验证、可集成的实施单元，并按依赖增量落地。单写者、代理派发和工作树隔离是拆分后的执行选择，不决定单元边界。

## 可复现失效模式

- 按文件、代码行数、提交或代理拆任务，会把一个需求结果切成无法独立成立的半成品。
- 把有未满足依赖的单元并行实施，会让后置工作依赖临时接口或尚未集成的状态。
- 旧版规模分档、固定切片阈值、强制交接模板和一单元一提交会增加流程成本，并诱导模型为满足仪式而错误拆分。
- 约束过轻时，模型可能把“增加类型”“补测试”或“派给代理”误当作完整实施结果。

## 目标模型证据

本轮未执行 GPT 5.6 Sol 或 Fable 5 的受控模型行为评测。处置依据是用户在目标模型上的实际使用反馈、旧技能的静态协议审查、仓库现有消费关系和 PR #191 的第一次正式深入评审。结论不表述为目标模型已经原生掌握所有拆分纪律。

## 与其他资产的关系

- `spec-design` 负责需求层的 Why、可观察行为、验收契约和必要的子规范分组；本技能消费已确认结果，不重新打开产品拆分。
- `arch-design` 负责领域模型、模块边界、接口和迁移形态；本技能沿用已确认设计形成实施单元。
- plan 阶段记录实施步骤与依赖；本技能复核任务是否构成完整单元并增量落地。
- `test-driven-development` 负责单元内部的失败证据或行为保护，`git-workflow` 负责语义提交边界，两者不由本技能重复实现。
- `deep-review` 独立审查整体差异；实施单元完成不等于拉取请求已经通过正式评审。

## 处置结论

结论为**精简**。删除固定规模档位、差异行数阈值、最低代理数量、固定切片仪式和强制交接模板；保留完整实施单元定义、需求结果拆分、依赖顺序、行为证据、单写者默认、隔离并行及跨运行时的模型、推理强度、工作树与通信能力。

PR #191 的第一次正式深入评审使用四个彼此隔离的内置评审上下文，覆盖需求符合性、文档同步、测试质量和技能插件质量。评审发现并修复：并行门禁未明确排除未满足依赖；验证契约没有逐项测试追溯且部分断言锁死措辞；工作流标题版本未随正文升级；长期索引与正式评审记录未同步。修复后没有自动触发第二轮深入评审。

## 风险与恢复条件

- **完整性约束不足**：如果正式评审或实际实现反复出现“单元结束但需求结果仍依赖未来补齐”，优先补充具体的边界判定或契约测试，不恢复固定行数与规模矩阵。
- **并行门禁不足**：如果多写者持续出现基于临时接口开发、重复集成或依赖尚未完成的问题，加强未满足依赖检查；只有确定性机制可以可靠执行时，才把对应规则下沉到工具。
- **约束过重**：如果技能再次明显压制模型基于实际代码选择更简单的实施方式，删除不能对应具体失效模式的细则，保留完整结果与合法中间状态两条底线。
- **模型证据缺失**：若后续需要宣称 GPT 5.6 Sol 或 Fable 5 已原生覆盖某项职责，必须另行执行受控评测；本记录不能作为该结论的证据。
