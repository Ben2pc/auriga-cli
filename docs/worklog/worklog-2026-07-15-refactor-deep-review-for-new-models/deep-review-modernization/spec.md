# Deep Review 现代化 — Spec (Deep Review 现代化 — 规范)

> 面向新一代模型重整正式拉取请求审查：保留独立多维评估，减少重复分派、错误触发和平台规则漂移。

## Why (为什么做)

`deep-review` 的独立评估仍然具有不可替代的价值，但现有编排把正确性与鲁棒性重复分派，使用过粗的变更标签，并长期背负旧版自定义审查者兼容逻辑。部分审查清单还把启发式规则写成硬缺陷，容易制造低价值测试、架构教条和没有证据的性能或安全发现。

这次升级不追求把审查者压缩到最短。正式审查可能由较低档模型执行，因此需要保留检查清单、检测表和典型例子；优化重点是消除职责重叠、修正错误规则、改善证据要求，并让主编排只承担路由与综合职责。

## Findings (调研发现)

- `plugins/auriga-workflow/skills/deep-review/SKILL.md` 当前分派 11 个内置审查者，其中 `correctness` 与 `robustness` 在空值、并发、副作用和错误路径上明显重叠。
- `plugins/auriga-workflow/skills/deep-review/SKILL.md` 当前把任何代码逻辑变更都判为非平凡，并让纯配置或文档变更进入不准确的统一分级；任意新增文件还会触发架构审查。
- `plugins/auriga-workflow/skills/deep-review/SKILL.md` 当前会读取旧版自定义审查者正文并猜测宿主，与“主代理只读取前置元数据”的隔离目标冲突；被吸收审查者的触发条件还可能失效。
- `plugins/auriga-workflow/skills/deep-review/references/reviewers/spec-conformance.md` 当前主要把文件化验证契约视为需求来源，未把当前对话中的一句话要求作为正式输入。
- `plugins/auriga-workflow/skills/deep-review/references/reviewers/docs-sync.md` 当前主要从差异里的文档开始检查，无法稳定发现代码事实变化但承重文档未更新的情况。
- `plugins/auriga-workflow/skills/deep-review/references/reviewers/architecture.md` 当前把贫血领域模型列为反模式，但数据与行为分离本身不是缺陷；真正风险是不变量泄漏和规则散落。
- `plugins/auriga-workflow/skills/deep-review/references/reviewers/skill-plugin-quality.md` 缓存了易漂移的平台事件与格式规则，同时要求每次审查抓取全部官方文档。
- `docs/rules/agent-portability.md` 要求 Auriga 同时服务多种编码代理；根 `AGENTS.md` 进一步规定以 `AGENTS.md` 为主入口并建立 `CLAUDE.md` 兼容入口。
- 本地同时存在 Claude Code 官方技能创建器与 Codex 系统技能创建器的 `quick_validate.py`，可以作为双运行时技能结构验证工具。
- 仓库不存在 `docs/rules/spec/`，本子规范没有额外项目专属规范规则。

## What (做什么)

### 1. 保留独立正式评估

正式审查继续由彼此隔离的全新上下文并行执行。每位审查者只接收原始差异、权威需求、适用的项目规则和自身参考文件，不继承实现会话，也不复用此前审查会话。任一必需审查者失败或缺少权威输入时，综合结果必须明确标记审查不完整。

### 2. 收敛审查维度与触发条件

将正确性与鲁棒性合并为一个审查维度，最终保留 10 个内置审查者。需求符合性和文档同步始终执行；其他审查者依据可执行行为、测试、长期维护代码、信任边界、用户界面、性能敏感路径、架构边界和代理扩展资产分别触发，不再使用单一的平凡/非平凡二分代替风险判断。

每个拉取请求第一次正式深度审查直接执行。此后若代理主动建议再次审查，必须先取得用户确认；用户已经明确要求再次审查时，不重复询问。

### 3. 扩展权威需求来源

需求符合性审查同时接受文件化规范、长期规范、任务或问题、当前对话中用户的原始要求以及用户最新明确决定。实现者撰写的提交说明、拉取请求技术理由和自主决定不能覆盖这些来源；拉取请求中的验收条件只能作为低优先级兜底。

### 4. 提升审查证据质量

各审查者保留足以支持较低档模型的详细检查表、检测信号和少量例子，但删除机械阈值与架构教条。安全、性能和用户体验审查先确定项目等级、暴露面、负载或支持平台；没有具体攻击路径、负载模型或可视证据时，不能把通用最佳实践包装成已确认缺陷。

测试审查以可观察行为和风险为中心，不要求固定场景数量、逐分支测试或没有契约价值的精确文本断言。架构审查不把贫血模型视为缺陷，只报告规则散落、不变量泄漏、职责错位和实质性设计偏差。

### 5. 同步事实并治理文档资产

文档审查从本次差异改变的事实出发，搜索未修改但可能漂移的承重文档；同时判断文档是否仍值得维护。有效建议可以是更新、删除、合并、压缩、归档或晋升，而不是只增加和改写文档。归档快照遵循仓库生命周期，不为追赶当前实现而改写。

### 6. 简化自定义审查者协议

项目自定义审查者必须使用前置元数据并明确声明吸收到哪个内置维度，或声明为独立维度。删除旧正文元数据回退和语义猜测。宿主或任一项目扩展的触发条件命中时都要运行宿主，并在综合结果中保留项目扩展来源。

### 7. 保持多运行时技能与插件质量门禁

技能与插件审查先识别目标运行时，再应用对应平台和项目规则。Auriga 继续要求 `AGENTS.md` 与 `CLAUDE.md` 同时存在，并同时使用 Claude Code 与 Codex 的官方技能验证工具；工具不可用时如实声明并回退到另一工具、项目测试和静态检查。

平台官方资料按差异需要查询，不在每次审查中无条件抓取全部文档，也不把审查者自身规则漂移作为目标拉取请求的发现。

### 8. 输出完整、可执行且不越权

综合结果保留所有范围内发现的严重度、置信度和来源，按同一根因去重，并单列缺失证据或未完成的审查维度。审查者可以给出具体修复方向和验证方式，但正式审查本身不修改代码、不创建问题、不发表评论，也不自主重做架构设计。

## Out of scope (本次不做)

- 不执行目标模型对照评测；用户已明确本轮先不做评测。
- 不自动修复审查发现、创建跟踪问题、提交拉取请求评论或重新批准架构决定。
- 不为旧版无前置元数据的自定义审查者提供迁移工具；团队可人工更新少量项目文件。
- 不把全部平台官方文档复制进审查者，也不承诺缓存平台的完整事件、字段或模型清单。
- 不修改与 `deep-review` 协议无直接依赖的其他工作流技能。
