# docent — Spec (代码讲解员 — 规范)

> 给 auriga-workflow 插件新增 `/docent` skill：用户给一个自然语言问题或路径，由单个专职子代理通读相关代码，生成一份自包含的交互式 HTML 讲解报告，帮人类快速建立对某段代码逻辑的正确心智模型。

## Why (为什么做)

Agent 写代码的速度已经远超人类阅读代码的速度。人类对代码库的心智模型持续落后于仓库的真实状态——尤其是 Agent 刚写完的部分。靠对话问答理解代码有两个缺陷：一是输出是线性文字，缺少图、表、可下钻的层级结构，理解效率低；二是阅读大量代码会污染主对话上下文。

现有的 `zoom-out` 类纯提示词 skill 只能改变 Agent 的回答姿态（"上升一层抽象讲"），产出仍是对话文字。docent 把"理解 xx 的代码逻辑"升级为一份可视化、可交互、可离线打开的理解制品。

一个关键场景是：用户自己也不知道需要理解哪些文件，只带着一个问题来（"xx 相关的代码逻辑是怎么回事"）。所以入口是问题而不是坐标，定位相关代码本身是 skill 的职责之一。

## Findings (调研发现)

- 参考对象 `zoom-out`（`~/.claude/skills/zoom-out/SKILL.md`，用户全局 skill）仅 430 字节，是 `disable-model-invocation: true` 的纯提示词，无制品产出。
- 插件内已有 HTML 报告先例：`plugins/auriga-workflow/skills/session-compound/`，产出自包含 HTML、写 `/tmp` 不落仓库。但它采用固定 `template.html` + analyzer 脚本结构；docent 经澄清决定不固定模板。
- 插件 manifest 当前版本 3.9.0（`plugins/auriga-workflow/.claude-plugin/plugin.json`）；`.claude-plugin/marketplace.json` 与 `.agents/plugins/marketplace.json` 的插件 description 中枚举了全部 skill 清单，新增 skill 需同步。
- 双 Agent 可移植性硬约束见 `docs/rules/agent-portability.md`：泛指 Agent 不写 "Claude"，Claude 独有工具名必须成对写出 Codex 对应物（如 `AskUserQuestion` / `request_user_input`）。
- 仓库已有针对插件 skill 的仓库级测试：`tests/plugin-skill-frontmatter.test.ts`、`tests/auriga-workflow-skills.test.ts`，运行器为 `node --test`（经 `npm test` 触发）。
- 按根 `CLAUDE.md` 版本规则：仅 `plugins/<name>/*` payload 变更时，freshness 由插件自己的 manifest 版本负责，不需要提升 CLI `package.json` 版本。
- 仓库本地有 `frontend-design` skill（`.claude/skills/frontend-design/`），含一套避免同质化"AI 默认审美"的前端设计准则（字体、色彩、动效、空间构图、背景与视觉细节）。按仓库规则 `.claude/` 只放本地设置与外部 skill 符号链接，插件资产不能按路径依赖它——需要摘取改编进插件自身。
- 无项目专属 spec 规则（`docs/rules/spec/` 不存在）。

## What (做什么)

### 1. 入口与触发

- skill 名为 `docent`，归属 auriga-workflow 插件，**仅限用户显式调用**（`/docent <参数>`），不允许 Agent 在普通对话中自动触发。
- 参数是一个自然语言问题（如"用户登录后 token 是怎么刷新的"）或一个仓库内路径（文件或目录）。
- 参数为存在的路径时，理解范围即该路径，跳过定位阶段；否则参数被当作主题，skill 先自行定位相关代码。两种入口共享同一产出契约。
- 无参数调用时，向用户询问想理解什么，不凭空猜测范围。

### 2. 执行模型

- 整个定位→通读→合成→生成的过程由**单个**专职子代理完成，保持对所讲逻辑的完整图景；不做并行碎片化阅读后由主 Agent 拼装。
- 子代理的作用是隔离上下文消耗：批量代码阅读发生在子代理内部，主对话不被其污染。

### 3. 产物形态

- 产物是**单文件、自包含、离线可打开**的交互式 HTML（打开时无运行时网络依赖），写入 `/tmp`，不落进项目仓库。
- 生成后自动用浏览器打开，并在主对话中给出文件路径和一段文字摘要。
- **不固定 HTML 模板**：skill 只规定核心目的、可视化手段调色板（时序图、流程图、状态图、对照表、可折叠多层级下钻、带锚点的代码片段等，按问题自选）和硬性质量约束；具体呈现形式由子代理针对当次问题自行设计。
- skill 自带一份**前端设计规范参考**（从 `frontend-design` skill 的审美准则摘取改编，随插件分发，不按路径依赖插件外资产）：要求报告在字体、色彩、动效、空间构图上有明确的设计立场，避免同质化的"AI 默认审美"。子代理生成 HTML 时必须参考该规范。它约束设计质量，不约束具体版式，与"无固定模板"不冲突。
- 修订记录（PR 实现期间的架构决策）：skill 另携带**机械组件资产**（design token、组件 CSS、数据驱动的 SVG 渲染器）与拼装脚本，由脚本注入产物、模型不重打。"无固定模板 / 不携带固定模板资产"的边界据此划定为：**版式、叙事结构、章节设计自由（不固定页面模板）；目录树、图表绘制等机械组件固定复用（组件库 ≠ 模板）**。动机：砍掉手绘 SVG 与重打样板的输出开销，并让渲染缺陷可以一次修复、全部报告受益。
- 报告语言跟随当次对话语言。

### 4. 报告内容契约（九条必答）

> 修订记录（PR Ready 后用户反馈）：原"文件角色"与"目录结构"两条合并为"代码地图"（带着结构讲定位）；原"定位透明"更名为更易懂的"阅读足迹"；新增硬性约束"主流程至少配一张标准软件工程图"。

一份合格的报告必须回答以下九个问题：

1. 这段逻辑为什么存在、解决什么问题；
2. 入口在哪、主流程怎么走；
3. 代码地图——把涉及的文件放在目录结构里讲：位置布局 + 每个文件的角色，不拆成两节；
4. 关键数据/状态如何流转；
5. 有哪些不明显的约束、坑、特例；
6. 与相邻模块的契约——对外承诺了什么、依赖谁、谁依赖它；
7. 历史演化脉络——从 git 历史看这段代码为什么长成现在这样（关键提交/合并的动机）；
8. 如何验证理解——重点是人如何端到端地验收或亲身体验这段逻辑（启动方式、操作路径、应观察到的行为）；自动化测试作为辅助佐证（修订记录：原表述以测试命令为主，按用户反馈改为以人工端到端体验为主）；
9. 阅读足迹——读了哪些文件、为什么认为相关、哪些可能相关但未深入。

范围很窄的问题（如单个小文件）允许把个别维度显式标注"不适用"，但禁止静默缺失。

报告中所有关于代码的结论都必须附带 `文件:行号` 锚点，可追溯到仓库中的具体位置；"入口与主流程"必须由至少一张标准软件工程图（时序图/流程图/状态图）承载，纯文字不能替代。

### 5. 纠偏循环

- 第 9 条"阅读足迹"的存在意义是让用户能发现定位偏差（"你漏看了 X"）。
- 用户在主对话中指出遗漏或偏差后，可在同一会话内要求修订，得到一份更新的报告；不引入任何跨会话持久化状态。

### 6. 发布同步

- 新增 skill 属于 plugin payload：提升 auriga-workflow 插件 manifest 版本，并把 `docent` 同步进两份 marketplace 清单的插件 description；不提升 CLI `package.json` 版本。

## Out of scope (本次不做)

- **变化模式**：解释一个分支 / PR / 最近 N 个提交引入了什么——留给后续版本（其"改动前后对比"的呈现是另一套设计，值得单独迭代）。
- **自然语言自动触发**：经澄清明确只走显式调用，普通问答（"这个函数返回什么"）不应生成重报告。
- **并行多子代理阅读**：碎片化阅读会切断跨文件因果链，明确排除。
- **固定 HTML 模板资产**：不随 skill 携带 `template.html` 之类的固定模板。
- **报告落仓库与跨会话累积管理**：报告是即时消费品，代码一改即过期，不做留存、索引或清理策略。
- **CLI `package.json` 版本提升**：本次变更纯属 plugin payload。

## Open questions (悬而未决)

1. 两个运行时（Claude Code / Codex）各自用什么机制派遣"单个专职子代理"——归属 **plan**；理由：运行时派遣机制是实现选型，不影响外部行为契约，但需要在 plan 阶段为两端分别确认可行做法。
2. 图表如何内联进单文件 HTML 以满足离线自包含（如 Mermaid 内联打包 vs 预渲染 SVG）——归属 **impl**；理由：渲染技术选型不改变"离线可打开"这一行为契约。
3. 范围过大、子代理上下文装不下时，"深入讲解 vs 仅列举"的取舍启发式——归属 **impl**；理由：契约已要求裁剪必须在"阅读足迹"一节可见，具体启发式属于实现细节。
