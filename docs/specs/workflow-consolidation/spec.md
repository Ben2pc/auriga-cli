# 工作流组合收敛 — Spec（工作流组合收敛 — 规范）

> 在单项技能完成现代化后，收敛 Auriga 常驻工作流的组合路由，减少重复上下文和不必要交互，同时保留人工决策与确定性门禁。

## Why (为什么做)

- **问题与用户**：Auriga 用户在进入实现、处理缺陷和完成拉取请求时，会同时受到 `AGENTS.md`、技能触发条件和 Hook 的组合约束。单项技能已经精简，但常驻入口仍复制技能细节、混合不同维度的执行选择，并保留弱模型时代的固定规模判据。
- **事实依据**：当前模板把内置 Plan、`planning-with-files` 与 `goalify` 放在同一个三选一菜单；快速流程按模块数和验收标准数量分诊；缺陷修复会同时命中调试与测试技能；合并后固定询问是否复盘；中英文模板还重复了多个技能正文已有的执行细节。
- **价值与时机**：单项技能评审已经完成，现在可以在不重开各技能核心职责的前提下统一组合协议。更短的常驻入口能降低所有任务的上下文成本，并让人工确认集中在真正需要选择的节点。
- **替代方案**：只继续精简单项技能无法消除总路由中的重复和冲突；完全删除常驻工作流又会失去人工门禁、技能路由、验证声明与拉取请求生命周期约束。

## Findings (调研发现)

- `AGENTS.template.zh-CN.md` 与 `AGENTS.template.en.md` 的受管区块当前各 70 行，顶部 11 条工作流中多处重复 `spec-design`、`arch-design`、`git-workflow`、`test-driven-development`、`incremental-impl` 和 `deep-review` 的正文。
- 内置 Plan 与 `planning-with-files` 都承担计划和进度载体，应在进入非快速实现前二选一；`goalify` 承担自主执行，可以与任一计划载体组合，不属于同一互斥维度。
- 当前快速流程使用“单模块、验收标准不超过 5 条、无跨边界接口变化”三个固定谓词，并无条件要求全量回归；这些信号不能稳定代表实现复杂度或验证范围。
- `systematic-debugging` 负责建立问题证据和确认根因，`test-driven-development` 负责进入修复实现后的失败证据与回归保护；两者应顺序触发，而不是在缺陷报告出现时同时加载。
- Ready 前询问当前拉取请求临时资料的去向属于用户确认门禁，继续保留。
- “持续对抗熵增”会指导评审发现的处置：在不扩大当前范围的前提下，小额偿还确定且低风险的技术债务，不能作为无执行含义的口号删除。
- `quality-gate-scaffolder` 是独立插件，其 5 个 Scaffold 技能不属于本轮工作流技能升级范围。
- 仓库不存在项目专属 `docs/rules/spec/`。

## What (做什么)

1. 常驻工作流保留需求澄清、架构确认、计划载体选择、Git 生命周期、缺陷与测试顺序、增量实现、完成声明、拉取请求就绪和正式评审等必要路由，但不复制技能内部流程。
2. 需要计划时，在进入实现前让用户从内置 Plan 与 `planning-with-files` 中二选一；`goalify` 只在用户明确选择自主执行时启用，并可与任一计划载体组合。
3. 快速流程改为语义判断：只有单一明确结果、没有未决产品或架构决定、不需要跨会话跟踪，也不需要拆成多个完整实施单元时，才跳过计划载体选择。
4. 缺陷先使用 `systematic-debugging` 建立证据并确认根因；进入修复实现后，再使用 `test-driven-development` 建立回归保护。
5. 保留 Ready 前询问当前拉取请求临时资料的删除或归档去向；保留跨拉取请求总规范的人工归档生命周期。
6. 合并后不再固定询问是否运行 `session-compound`；只有用户明确要求复盘或洞察时才触发该技能。
7. 文档目录表保留 `docs/rules/` 总入口，删除没有具体路由价值的 `docs/ 其他` 行。
8. 运行框架原则保留机制优先、仓库事实源、持续对抗熵增和分层指令入口；删除由具体技能完整表达的独立评估原则，以及只服务 Auriga 自身演进的组件可拆卸原则。
9. 代理分发说明保留写入隔离、原生代理优先、独立进程边界和派遣契约，删除固定模型档位与推理强度映射。
10. 中英文模板、仓库示例 `AGENTS.md`、相关技能触发与交接文字、测试和长期总规范保持一致。

## Out of scope (本次不做)

- 不重新设计已经完成单项评审的 13 个工作流技能核心流程。
- 不删除内置 Plan 与 `planning-with-files` 的二选一确认。
- 不删除需求价值、实质性架构决定或 Ready 临时资料去向的人工确认。
- 不降低首次正式 `deep-review`、验证声明或 Git Hook 的确定性门禁。
- 不评审或修改 `quality-gate-scaffolder` 的 5 个 Scaffold 技能。
