# session-compound 现代化 — Spec (session-compound 现代化 — 规范)

> 同时提供单次任务复盘与近期使用洞察，让建议建立在可信证据上，并把“值得尝试”与“值得长期沉淀”明确分开。

## Why (为什么做)

`session-compound` 的独立价值，是把已经发生的 Agent 工作转换成可人工复核的证据：这次任务发生了什么、执行得怎样、哪些经验值得进入长期工程上下文。这个闭环仍然有价值，尤其适合长程任务、多人共用工作流，以及需要从真实执行表现反向优化技能的场景。

但当前流程只看一个会话，并把“复盘”与“必须找出若干改进”绑定在一起。候选数量下限、无条件生态搜索和复杂分类规则会推动模型把一次性问题、工具自身缺陷，甚至已经被现有技能吸收的用户反馈包装成新的长期规则。生成的内容表面完整，却难以理解，也没有实际沉淀价值。

Claude Code Insights 展示了另一种有价值的产品表面：汇总近期多个会话，先识别工作领域、交互方式、有效模式和反复摩擦，再提供现有功能、可复制提示词和更有野心的工作流建议。它的“值得尝试”比当前沉淀候选更有帮助，关键原因不是措辞更丰富，而是它利用跨会话重复证据，并允许建议先作为低承诺实验，不要求立即写进长期规则。

报告中的基础事实仍必须可信。Codex 的正常技能使用经常表现为读取适用的 `SKILL.md`，而当前分析器只识别显式 `<skill>` 注入，因此真实使用过多个技能的会话仍可能显示“技能调用次数为 0”，并导致后续技能执行评估被整体跳过。类似地，非零工具退出既可能是测试驱动开发中的预期失败，也可能是真正的操作错误，不能未经判断全部称为浪费。

这次升级因此提供两种明确模式：单会话模式用于任务复盘，近期洞察模式用于最近 30 天的跨会话模式与教练建议。两者共享可信证据和人工确认边界，但不强行使用同一套报告结构。没有值得尝试或长期沉淀的内容时，零建议、零候选都是正确结果。

## Findings (调研发现)

- `plugins/auriga-workflow/skills/session-compound/SKILL.md` 当前要求产出 3–8 条候选，并在原始材料稀少时优先产出 1–3 条技能缺口；它还要求候选生成前固定执行生态搜索。这些要求与“宁缺毋滥”相互冲突。
- `plugins/auriga-workflow/skills/session-compound/analyzers/codex.mjs` 只从 `<skill><name>` 块统计技能调用；`tests/session-compound-analyzers.test.mjs` 进一步把“没有该块就必须返回空技能列表”固化为测试契约。
- 2026-07-16 对归档会话 `019ebfea-56c7-7361-9249-64713c2a4225` 的实测中，原始记录包含 61 次 `SKILL.md` 读取、涉及 17 个不同技能，按“技能 × 用户轮次”合并后仍有 42 次使用事件，但报告显示技能调用次数为 0。
- 同一次实测中，独立评估返回 26 条发现，但因为 `health.skills` 为空，没有生成任何逐技能执行评估；这说明错误计数不仅影响健康度展示，也缩小了评估范围。
- 该会话的 7 次用户纠正已经全部体现在当前质量门禁技能中，本应得到零条沉淀候选；现有流程仍生成了两个围绕 `session-compound` 自身局限的候选，用户无法理解其含义，也无法从中得到可执行价值。
- 该报告统计了 33 次非零工具退出，其中混有预期的失败测试、存在性探测和真实操作错误；原始退出事实有价值，但直接将总数解释为浪费会误导评审者。
- 归档会话通常不保存会话发生时完整的技能目录与工作流规则。分析器当前从执行报告时的仓库和安装目录读取这些内容，因此它能做“按当前规则回看”，但不能默认声称还原了历史现场。
- 用户提供的 Claude Code Insights 报告覆盖 2026-06-08 至 2026-07-16 的 23 个有效会话和 382 条消息。它把跨会话重复模式组织为项目领域、交互风格、亮点、摩擦、现有功能、新用法和未来工作流，并在顶部二次压缩为“有效模式、阻碍、快速尝试、进阶工作流”四段一览。
- 用户提供的 Insights 提示词显示，其分析分为纯代码统计、逐会话语义切面、多个单职责报告章节和最终一览合成，最后再由确定性代码渲染报告。逐会话切面只统计用户明确提出的目标与满意度信号，报告建议则同时使用统计、会话摘要、摩擦详情和用户指令。
- Insights 的建议分成三种不同价值：反复出现的用户指令可建议进入 `CLAUDE.md`，现有功能与新用法作为可复制的低承诺尝试，未来工作流负责启发而不要求立即采用。这比当前把所有发现都压成“落库候选”更符合实际决策成本。
- Insights 仍有需要避免的偏差：提示词固定要求若干条目，可能继续制造弱建议；报告会把已经在使用的模型上下文协议服务器当成新功能推荐；所有 `CLAUDE.md` 建议默认勾选，也会放大未经人工判断的持久化风险。
- `docs/worklog/worklog-2026-05-29-feat-session-compound-skill-eval/` 已确立独立新上下文评估的产品契约，用于降低实现者自评偏差；本次发现针对输入证据、跨会话洞察和建议闭环，不否定该独立评估职责。
- EveryInc 的 Compound Engineering 将一次运行聚焦为一个已解决问题的持久资产，并用独立维护循环处理保留、更新、合并、替换和删除；`reflect`、`reflect-skills` 等方案也把“没有洞察”与人工批准视为合法结果。这些资料支持减少强制产出，但不直接作为 Auriga 的运行时依赖。
- 仓库不存在 `docs/rules/spec/`，本规范没有额外的项目专属需求规格规则。

## What (做什么)

### 1. 每次先选择报告模式

每次调用 `session-compound` 时，先让用户选择本次要生成：

- **单会话复盘**：分析当前或用户指定的一次会话，聚焦该任务的过程、结果、执行质量和可处理问题。
- **近期使用洞察**：分析当前运行时最近 30 天内可读取的会话，聚焦跨会话工作模式、反复摩擦和值得尝试的能力。

技能不根据模糊措辞替用户默认选择，也不在一次调用中同时生成两份报告。近期洞察必须显示实际覆盖日期、发现的总会话数、成功分析的会话数，以及因过短、损坏或证据不足而未纳入语义分析的数量。

Claude Code 与 Codex 各自分析当前运行时能够访问的会话历史。合并两个运行时的历史不属于本次范围。

### 2. 单会话模式保留任务级审计

单会话报告继续覆盖会话叙事、执行健康度、独立评估和沉淀候选四类信息，并让用户能够从重要结论追溯到原始证据。

缺少某类证据时，报告必须明确显示“不可判断”或对应的证据限制，而不是用零值伪装“没有发生”，也不能因为某个区块为空而破坏整份报告。相同输入应能稳定生成结构完整的报告，不要求执行者人工修改报告源码才能完成交付。

### 3. 近期洞察模式提供跨会话教练报告

近期洞察报告至少回答以下问题：

- 最近主要在处理哪些项目领域，Agent 在其中承担什么角色。
- 用户如何与 Agent 协作，哪些交互方式已经有效。
- Agent 侧和用户侧分别有哪些反复出现的阻碍，具体后果是什么。
- 哪些当前运行时已有能力、工作方式或可复制提示词值得尝试，以及为什么适合这些真实会话。
- 随模型能力增强，哪些更长程或更自主的工作流值得逐步试验。

报告顶部提供简洁一览，分别概括有效模式、主要阻碍、可立即尝试的改进和更进阶的工作流。正文保留支撑这些结论的领域、亮点、摩擦和代表性会话证据；不能只给统计数字或泛化的人格描述。

同一模式只在多个独立会话中出现时，才能被表述为“反复模式”。最近 30 天样本不足以支持趋势判断时，报告可以提供事实摘要和单次观察，但必须明确证据稀少，不生成跨会话趋势或长期沉淀候选。

### 4. 区分洞察、值得尝试和长期沉淀

报告中的输出按承诺成本分为三层：

1. **洞察**：帮助用户理解工作方式、有效模式和摩擦，不要求采取行动。
2. **值得尝试**：建议使用已有能力、新工作方式或可复制提示词进行低成本试验；说明为什么适合、如何尝试，但不默认写入工程规则。
3. **长期沉淀候选**：只有用户明确要求长期保持某种行为，或同一纠正、约束、流程在至少两个独立会话中重复出现，才进入候选评估。

已经安装或频繁使用的能力不能被包装成“尚未尝试的新功能”；如果建议的是该能力的新用法，必须明确说明新增的是使用方式而不是能力本身。所有建议都允许为空，不设置条目数量下限。

### 5. 区分已确认调用与推断使用

技能使用必须按证据性质分别呈现：

- **显式调用**：运行时提供了明确的技能调用或注入事件，可以精确计数。
- **推断使用**：会话读取了某个技能的 `SKILL.md`，可以确认该技能进入了本轮工作上下文，但不能冒充运行时原生调用事件。

推断使用要按有意义的执行事件去重，避免同一用户轮次中的重复读取、分段读取或路径别名把一次使用放大成多次。只要任一类证据表明技能实际进入过工作过程，健康度不能显示为“未使用任何技能”，逐技能执行评估也必须把它纳入可评范围，同时保留其证据标签。

Claude Code 与 Codex 可以使用各自能够提供的原生证据，但共享概念、空态语义和报告解释必须一致。

### 6. 把事实、判断和证据限制分开

分析器先保留可验证的原始事实，报告或独立评估再对事实作判断：

- 非零退出、失败测试、取消操作和重试不能自动等同于浪费；报告应区分原始失败事实、可识别的预期失败，以及有证据支持的异常或无效消耗。
- 工作流规则和技能目录必须标明来源时点。无法获得会话发生时版本时，只能表述为“按当前规则回看”，不能把当前状态写成历史事实。
- 证据不足时不推断精确数字、违规结论、重复模式或技能表现；未知状态必须对人可见。
- 模型判断出的满意度、摩擦、帮助程度和趋势必须标明为分析结论，并能回到明确的用户信号或代表性会话，不能伪装成机械统计。

### 7. 让零候选成为正常结果

报告不再设置候选数量下限。只有当直接证据支持一个未来仍可能重复、会改变后续行为、处于团队控制范围内且尚未被现有资产吸收的问题时，才提出长期沉淀候选。

每条候选必须让没有参与相关会话的人也能快速理解：它来自什么证据、反复发生的模式是什么、未来行为要怎样改变、建议更新哪类资产。以下情况不生成沉淀候选：

- 用户反馈已经被当前代码、规则、文档或技能完整吸收。
- 一次性操作失误、偶发环境问题或没有复发依据的现象。
- `session-compound` 自身的分析或渲染缺陷；这类问题应作为报告可信度问题修复，不包装成被复盘项目的经验。
- 上游工具或外部资产问题，且团队无法在目标工程内采取有效行动。
- 只有宽泛愿望，没有可追溯证据、明确行为改变或合理落点。

没有条目通过这些条件时，候选区明确说明本次没有值得长期沉淀的改进。这是成功完成复盘，而不是内容缺失。

### 8. 只在真实需要时搜索生态

生态搜索不再是每次复盘的固定步骤。只有会话证据已经支持“需要新增或安装一个技能”的长期候选，并且现有工程资产没有覆盖该模式时，才搜索是否已有可复用技能。搜索结果必须与对应候选绑定；没有真实技能候选时，不产生搜索成本，也不把搜索结果倒推成需求。

近期洞察中的“值得尝试”优先从当前运行时真实可用、且用户尚未采用的能力中选择，不依赖开放式生态搜索凑满列表。

### 9. 保留独立评估，但不让评估自动变成候选

单会话模式中的指令遵循、技能召回和技能执行表现继续由独立新上下文评估完成，以降低原会话执行者自评的偏差。评估应收到带证据标签的技能使用事实和证据限制：召回分析可以检查适用目录，执行表现只评价本会话有使用证据的技能。

评估发现继续携带严重程度、置信度和证据，不因模型可能判断错误而提前隐藏；但评估发现必须经过候选条件，不能一一自动转换为长期规则或技能改动。近期洞察中的语义结论同样要与原始统计分离，并保留代表性会话证据。

### 10. 坚持人工确认与职责分离

`session-compound` 只负责发现、解释和提出建议，不自动安装技能，也不直接修改工程文件。洞察和“值得尝试”默认只是报告内容；长期沉淀候选也不默认选中。用户明确确认要采纳的条目后，再由对应能力处理详细落库：工程文档与长期上下文交给 `documentation-management`，技能创建或优化交给 `skill-creator`，项目审查者交给 `reviewer-creator`。

## Out of scope (本次不做)

- 不生成跨 Claude Code 与 Codex 的合并洞察；每份近期报告只分析当前运行时的历史。
- 不聚合多位团队成员的会话，不做团队排行榜或个人绩效评估。
- 不自动应用建议、安装外部技能或修改项目文件。
- 不重写 `documentation-management`、`skill-creator` 或 `reviewer-creator` 的内部流程。
- 不承诺从缺少历史快照的归档日志还原当时完整的规则与技能目录。
- 不建立 GPT 5.6 Sol、Fable 5 或其他模型的通用评分基准；本次验收关注报告契约和证据质量。
- 不以本次规格为由重新设计视觉风格；两种模式可以使用不同信息结构，但不追求独立的设计系统。

## Open questions (悬而未决)

1. 推断使用的具体事件窗口与路径归一化算法归属 **impl**；本规范只要求不漏掉真实使用且不被重复读取放大，推迟是因为不同运行时日志结构不同。
2. 预期失败、异常失败和未知失败的具体分类信号归属 **plan / impl**；本规范只要求原始事实与判断分离，推迟是为了基于两种运行时实际可用字段选择可靠口径。
3. 单会话与近期洞察如何共享分析、缓存和渲染能力归属 **plan**；本规范只要求两种报告稳定生成且不依赖人工修改报告源码，推迟是因为内部模块边界不属于用户行为契约。
