# 规格与架构设计模板可读性 — 规范

> 让 `spec-design` 和 `arch-design` 产出的文档，评审者第一屏就能看到重点和要拍板的事，其余按需查阅：技能写明核心写作原则和自检，模板规定写什么、不写什么、写在哪里，而不是只要求写全。
> 状态：已确认；样例重写评估后的几处澄清（见[验证结果](validation-results.md)的验证记录-003）待 Ben 确认。确认记录见第 6 节。

## 1. 产品总览

### 1.1 为什么做

- **问题与用户**：
  - 评审者（目前主要是 Ben）要在实现前确认规格和架构设计，但按现有模板写出的文档长、散、没有重点，读不下去；读不下去就会跳读或直接批准，人工确认失去意义。
  - 实施和排查的 Agent 要从文档里找契约和事实，决定、理由、实现细节和历史记录混在一起，同一件事要对照好几处。
  - 写作的 Agent 照模板填满每个格子：模板几乎只有“必须写全”的规则，没有“什么不写”和篇幅上限。
- **事实依据**（2026-10-26，详见 1.4）：
  - 服务平台的架构设计 14.2 万字，是对应规格合计的 3.3 倍；给评审者拍板的内容只占 4%；同一决定写在 6 处；
  - 11 份客户端和后端架构设计、8 份规格样本里反复出现同几类问题：字段名生硬、为填格子写空话、拍板项不在文首、来源和需求在三处重复、表头中英混写、核对类表格的第一列不是被核对的对象、修订往后追加而不改正文；
  - 8 份规格样本没有一份用模板里的交互设计表和文案契约表；
  - 团队近期三份产品需求文档好读，靠的是：文首一句话需求和状态，按页面组织，规则、异常和数值都用表格，红线规则一句话一条，待决事项集中在一处。
- **改写样例**：按本规范方向手工改写服务平台架构设计（临时目录，未提交），正文降到原文的 37%，决策页约 1300 字。
- **价值与时机**：服务平台还有五个以上实施单元要评审，后续每一份规格和设计都沿用这两套模板；现在改，后面每份文档都受益。Ben 2026-10-26 要求把这些问题记录成规格，并把规格模板一起纳入。
- **替代方案**：
  - 不做：评审者继续跳读或延迟评审；
  - 只人工瘦身现有文档：下一份照旧膨胀，问题在模板；
  - 只加字数上限：模型会压缩措辞，但重复、层级过深和读者混杂这些结构问题仍在。

### 1.3 整体产品体验

- **目标用户与场景**：评审者确认规格或设计；实施与排查的 Agent 查契约和事实；写作的 Agent 按模板写文档。
- **端到端结果**：评审者打开一份规格或架构设计，第一屏看到要做什么、不做什么、关键决定和待确认问题；往下是按产品功能或需求主题组织的详情，规则和异常用表格；事实、来源和确认记录在附录或文末，不挡阅读。
- **共享规则**（两类文档都遵守，分项按编号引用；2.4.1 把它们原样写进两个技能）：
  - **R1 首要读者是评审者**，其次是实施的 Agent；优先于“未指定读者时面向 Agent”的通用默认。
  - **R2 先给重点**：首屏（要点页或决策页）让评审者不往下读也能拍板。
  - **R3 一事一处**：每个决定、规则、模型、接口和事实只定义一次，其他位置用带名字的链接或规则编号引用。
  - **R4 只写要评审的内容**：规格不写技术方案和实施过程；架构设计只写跨边界契约和需要拍板的选择。
  - **R5 能用表就不写段落**；核对类表格第一列放被核对的对象（指标名、告警名、风险、路径、场景、文案位置）。
  - **R6 中文常用说法、短句、按需填写**：字段名读者不查定义就懂；按需字段没有内容就删，不写“无”。
  - **R7 修订就地更新**：评审意见、确认结果和实现中的变化直接改正文，历史由版本库保存。
  - **R8 篇幅与改动规模相称**：小改动只有首屏和一两个分项；附录可以长，但不挡阅读。
- **总体范围**：2.1 至 2.4。只对新写和大幅改写的文档生效（Ben 2026-10-26 确认），已有长期规格在下一次落地瘦身时顺带改。

### 1.4 调研发现

**现有技能与模板**

- `arch-design/SKILL.md` 第 4 步指定模板是唯一详细契约；第 5 步的理由闭环要求理由就地写进机制旁，需求闭环要求逐条反查；第 6 步规定拉取请求就绪前晋升、归档或删除。
- 架构设计模板 27,346 字节，规格类四个模板合计 23,418 字节（规格 8,851、伞形 5,990、验收契约 5,444、验证结果 3,133）。
- 仓库检查只覆盖 `arch-design/SKILL.md` 与 `spec-design/SKILL.md` 读取各自规则目录，没有模板结构的检查（`tests/auriga-workflow-skills.test.ts`）。本仓库没有 `docs/rules/spec/`。
- 两个技能都没有写作原则：`arch-design/SKILL.md` 只说“写出可人工评审的设计”，`spec-design/SKILL.md` 只说帮助人类确认；写作要求全部压在模板里。`documentation-management` 规定“用户未明确指定读者时默认面向 Agent”，而规格和设计的首要读者其实是评审者。
- 其他技能依赖现有结构：`test-driven-development/SKILL.md` 按验收契约的“验证方式”选证据；`incremental-impl/SKILL.md` 读取已确认的 `arch_design.md`；`arch-design/references/interface-design.md` 引用“人工评审重点”。技能之间已有按相对路径引用彼此参考资料的先例（`../spec-design/references/validation-results-template.md`）。
- 现有技能篇幅：`spec-design/SKILL.md` 14,081 字节，`arch-design/SKILL.md` 9,506 字节。
- 修改指令要替换、合并或删除旧表述，不只追加例外；技能资产要对 Claude Code、Codex 和 Cursor 都成立；只改 `plugins/auriga-workflow/` 时按插件自己的版本判断，不提升 CLI 版本（`AGENTS.md`、`docs/rules/agent-portability.md`）。

**架构设计样本**（两个只读子代理分别通读 iOS 3 份、Android 3 份、后端 5 份；另有服务平台一份）

- 字段名生硬、硬填：“有效状态规则：无状态。”“同一性判断：无独立同一性。”；“成立边界”被写成验证手段；只有一份客户端样本完整用了模型字段组。
- 模型混放：会话、界面卡片、接口客户端和请求类型同表；方法 `list_openable_series` 被当成模型。
- 接口字段啰嗦：“输入语义：不变。”；成功语义和示例重复；一个返回布尔值的函数拆成三条语义。
- 观测与风险表第一列是类别或维度；一份后端样本的 23 条告警没有一条有名字。
- 同一批文件列三遍；同一条理由出现五次；新建表的结构变更表有 26 行“不存在”。
- 修订追加“本节取代前文”；分支名、实施单元表、生产核查流水混进设计；迁移字段“负责人：本 PR 实现者”；后端术语不解释。
- “原始需求写成大段”在小样本里不成立，问题反而是只给编号或搬运规格文案；服务平台那份把规则文件罗列成八条。

**规格样本**（一个只读子代理通读三个仓库的 8 份规格及验收契约）

- 拍板项不在文首：文首只列已确认事项的名称、不写结论；未定参数放在最后一节；新决定只写进验收契约，规格状态停在旧日期。
- 固定小节重复：同一条需求在来源表、叶子“原始产品需求”和验收契约覆盖表出现三次；“事实依据：见 1.4”这类空引用。
- 表头中英混写：验收契约覆盖表的表头、“why + 用户可观察的 what”；待决归属写“arch / plan / impl”，伞形模板写“架构 / 计划 / 实现”，两处不一致。
- 交互设计表有 6 列、文案表的“最终文案”在第 3 列，8 份样本无一使用，文案被塞进段落。
- 验收契约的“验收要求”和“通过标准”意思重复；同一句验证方式重复 13 次。
- 平台类需求硬套产品字段：Agent 自己的建议被写成原始需求；带代码路径的调研发现排在需求前面。
- 同一模板产出两种叶子写法（编号小节与粗体字段）；三级验收映射难查。
- 值得保留：一句话讲清决定、状态行引用用户原话；共享规则编号为 R1 到 R5，叶子按编号引用；场景对结果的表格；验收要求与通过标准合成一张表。

**产品需求文档**（2026-10-26 以用户身份读取三份飞书文档：选剧换剧、角色抽卡玩法感知优化、连胜与钻石）

- 文首给一句话需求，或一个状态块写清负责人、状态、范围和标记约定（待决、跨单元、待设计）。
- 按页面或功能点组织：“页面、需求、示意图”或“功能点、为什么做、具体改动点、示意图”。
- 规则、数值和异常都是表：“事项、规则”“算不算、学习内容”“场景、例子、结果”；数值表注明“当前配置、可调”。
- 关键产品规则（红线）一句话一条；“已有功能兼容”一张表列出不变与变化；术语放附录。
- 指标表第一列是指标名，文案表第一列是位置；待决事项集中成一张表，写明现状和需要谁确认。

## 2. 产品需求分项

### 2.1 两类模板共同的规则

#### 2.1.1 中文字段名与按需字段

**原始产品需求**：来源 Ben 反馈第 2 条和规格模板反馈。字段名像英文直译，读者看不懂；不是每个字段都要写满。

**用户可感知行为**：

- 字段名用中文工程师的日常说法，一个字段名只表达一件事。架构设计模板的改写：

  | 现有字段 | 改为 |
  |---|---|
  | 人工评审重点 | 决策页（2.2.1） |
  | 同一性判断 | 唯一标识（实体）；相等规则（值对象） |
  | 状态与存续范围 | 生命周期 |
  | 有效状态规则（成立边界：……） | 规则（检查时机），例如“同一前缀只声明一次（登记校验时）” |
  | 约束与不变量 | 硬约束 |
  | 代码或存储映射 | 代码位置 |
  | 变更状态：已有保留、已有调整、本次新增、计划移除 | 不变、修改、新增、删除，写进模型标题（2.2.7） |
  | 原始需求、承接需求 | 需求、承接（2.2.3） |
  | 使用方 | 调用方 |
  | 输入语义、输出语义、错误或失败语义 | 输入、返回、失败（2.2.8） |
  | 成功或输出语义 | 删除，响应示例已经表达 |
  | 重复调用、投递与重放 | 重复请求，只在写操作和消息上写 |
  | 请求 DTO、成功响应 DTO、错误响应 DTO | 请求、成功响应、错误响应 |
  | 设计理由、职责落点说明 | 取舍卡，只在非显然时写（2.2.2） |
  | 图示说明与设计理由 | 看图要点，按需 |
  | 观测维度、风险维度 | 名称、风险（2.1.2） |
  | 内部接缝、接口实现映射 | 内部接口、替换点 |
  | 人工确认结果、参考依据 | 确认记录（2.1.3）、事实依据（2.2.5） |

- 规格类模板的改写：

  | 现有字段 | 改为 |
  |---|---|
  | 整体产品体验、悬而未决 | 要点页（2.3.1） |
  | 原始产品需求（来源、原始需求） | 需求一到三句，加一行来源（2.3.2） |
  | 用户可感知行为的六个字段 | 场景表、规则表、异常表（2.3.2） |
  | 分项范围边界（本项包含、本项不包含、引用共享规则） | 删除；容易误解时写一行“不包含”；共享规则按编号引用 |
  | 验收映射 | “验收”一行编号（2.3.2） |
  | 交互与动效六列表 | 状态表加按需的动效与无障碍要点（2.3.3） |
  | 来源结构对齐、调研发现 | 附录的需求来源与事实依据（2.3.4） |
  | 验收要求、验证方式、通过标准三个并列字段 | 一张表：编号、验收什么、通过标准、证据（2.3.5） |
  | 覆盖总览的英文表头、“why / what”“arch / plan / impl” | 只用中文：为什么、做什么、架构、计划、实现 |

- 模板给每个字段和章节标“必填”或“按需”。按需的没有内容就整行或整节删掉，不写“无”“不适用”“不变”；只有要点页或决策页的“待确认”在没有时写“无”。
- 架构设计的必填章节只有决策页和分项设计；规格的必填章节只有要点页和需求详情。
- 占位提示写短，只说要填什么；字段名不用英文缩写，代码实体名、协议名照原样。
- 评审者不熟悉的技术名词第一次出现时，用一句话说明它做什么。

**范围边界**：四份架构参考资料（组件、接口、领域建模、迁移）不改正文，只同步它们引用到的旧字段名。

**验收映射**：`VAL-FIELD-NAMING-001` ～ `004`。

#### 2.1.2 核对类表格第一列放被核对的对象

**原始产品需求**：来源 Ben 反馈第 4 条和举一反三。可观测设计的表格第一列应该是指标名或告警名，扫一眼就知道有没有漏。

**用户可感知行为**：

- 架构设计的可观测设计按类型分表，第一列是准确名称，一个名称一行，不合并多条：指标表（指标名、维度、统计什么、回答什么问题）；告警表（告警名、触发条件、接收方、怎么处理）；事件表（事件名、参数、什么时候记录）。日志只用短段落说明哪部分逻辑加日志。可观测设计只定义信号和处置，恢复流程、权限这类机制写在分项。
- 质量风险表第一列是风险本身（一句话），维度需要时写在括号里。
- 同一原则用在其他清单：退场清单第一列是路径，迁移阶段表是阶段，错误表是情况，文案表是位置，待确认表是问题，指标口径表是指标名。

**验收映射**：`VAL-SCAN-FIRST-COLUMN-001` ～ `004`。

#### 2.1.3 修订就地更新与确认记录

**原始产品需求**：来源样本证据和 R7。修订往文末追加“本节取代前文”，正文不同步；状态行写成长段的确认来源和迁移历史。

**用户可感知行为**：

- 评审意见、确认结果和实现中的变化都直接改正文，不追加“取代前文”“保留为历史”“某单元实现后的设计回写”这类段落。
- 文首状态只写一行：当前状态，以及哪些部分已确认、哪些待确认。
- 确认记录放在文末（架构设计放附录），一张三列表：日期、确认的决定、正文位置；可以引用用户原话，不复述决定内容。

**验收映射**：`VAL-REVISION-001`、`002`。

### 2.2 架构设计模板

#### 2.2.1 决策页

**原始产品需求**：来源会话建议第 1 条及 Ben 追问。开头是一屏以内的决策页，评审者读完就能拍板；它是总设计第 1 节，不单独成文件。

**用户可感知行为**：

- 第 1 节固定是决策页，依次包含：一段话说清改什么；修改已有系统时改变前后两张同一抽象层级的图（全新系统只画目标图）；三到五行编号的核心决定表（决定、决定性理由、代价、详见），每条先写一句结论；对外可见的变化（重构时必填，没有写“无”）；一到两条首要风险；编号的待确认项和暂缓事项。
- 正文不超过 1500 字，不含图（Ben 2026-10-26 确认）；决定更多时，其余降为分项里的取舍卡。
- 不放修订历史、已确认项的复述和逐条日期。

**验收映射**：`VAL-DECISION-PAGE-001` ～ `003`。

#### 2.2.2 取舍卡

**原始产品需求**：来源会话建议第 2 条。非显然的选择用固定格式的取舍卡说明理由，替代把机制、被否方案、边界情况和交叉引用揉进同一段的散文。

**用户可感知行为**：

- 机制正文只写“是什么”；理由写在紧跟其后的取舍卡里。
- 格式固定：标题“取舍：<选择>”；“理由”“代价”必填；“放弃”（有真实候选时）和“何时重新评估”按需。被否方案和排除项集中写在“放弃”里，正文不用一串否定句描述设计。
- 方向显然时不写，不编造候选；一个选择只有一张卡。`SKILL.md` 的理由闭环改为检查非显然选择都有就近的取舍卡。

**验收映射**：`VAL-TRADEOFF-CARD-001`、`002`。

#### 2.2.3 只写要评审的内容

**原始产品需求**：来源会话建议第 3、4 条和 Ben 反馈第 3 条。给出“写不写”的判据；每件事只定义一次；原始需求几句话说清。

**用户可感知行为**：

- **写入判据**：只写跨模块、跨服务或对外的契约，以及改变它需要评审者重新拍板的选择。实施者读代码就能得出的细节不写，例如被排除项的逐个列举、模块内部参数、完整函数签名；分支名、实施单元表、提交拆分、操作流水分别属于计划、验证结果和工作记录。
- **契约照常展开一次**：接口请求与响应、消息载荷、登记格式完整展示一次，不受篇幅压缩；重复出现的形状引用首次展示的位置。
- **需求追溯**：每个分项开头两行。“需求”用一到三句话说清要解决什么，不复述规格原文和界面文案、不罗列规则文件、不能只写编号；“承接”列验收编号和确实约束设计的规则。规格里每个验收编号都恰好出现在一个分项的“承接”里，或写明不适用。这两行替代原来的“原始需求”小节和参考依据表。
- **目录分两层**：总览一棵模块级落点树；分项保留本项的局部目录树，列出涉及的文件并标新增、修改、移动或删除，每行一句职责或改了什么（Ben 2026-10-27 确认）；删除资产的反向引用闭包只在附录的退场清单。

**验收映射**：`VAL-WRITING-SCOPE-001` ～ `004`。

#### 2.2.4 表格、图与导航

**原始产品需求**：来源会话建议第 5 条。能用表或图的不写成段落；标题不超过四级；交叉引用写成带名字的链接。

**用户可感知行为**：

- 三个及以上的条件分支写成表；三个及以上、有分支或回退的状态画状态图并配“状态、行为、能否退回”表，线性的生命周期写一行流程。
- 模块或依赖关系改变时必须有前后对比图；图里写业务含义，不写完整调用签名或查询语句；其余图类型按评审问题选择。
- 标题最多四级；不再用 `3.1.2.1.1` 式的固定编号小节，删除“保留层级编号”的约定；交叉引用写成带名字的链接，不写裸章节号。

**验收映射**：`VAL-NAVIGATION-001`、`002`。

#### 2.2.5 附录

**原始产品需求**：来源会话建议第 4 条后半。事实依据和资产退场清单移出阅读路径。

**用户可感知行为**：

- **事实依据**：每条自带来源（路径、版本或读取日期）；正文只在用到的地方写结论，原来单列的参考依据表并入这里。
- **资产退场清单**：仍按反向引用闭包逐路径列举、不用概括措辞；列精简为路径、资产、处置，可按实施单元分组标进度。
- **确认记录**：按 2.1.3。附录不计入决策页上限，不要求压缩；短文档放在同一文件末尾。

**验收映射**：`VAL-APPENDIX-001`、`002`。

#### 2.2.6 长期规格的设计拆分与落地瘦身

**原始产品需求**：来源会话建议第 6 条前半。规格拆成子规范时设计也跟着拆；子规范全部落地后压缩它的子设计。

**用户可感知行为**：

- 存在 `umbrella.md` 时，设计拆成一份总设计和每个子规范一份子设计。总设计只放决策页、设计边界、模块落点、被两个以上子设计使用的共享模型、子设计索引（含进度）、上线阶段、跨子设计的风险和附录；子设计放在对应子规范目录，状态行和分项设计必填，单独评审时保留一页简短的决策页。
- **落地即瘦身**：子规范的实施单元全部上线后，在登记上线结果的同一个拉取请求里，把子设计压缩为已确认的决定、稳定文档或代码的链接、已知差异和验证结果链接；被移走的内容先由 `documentation-management` 晋升到稳定文档、架构决策记录或局部指令，没有落点的不能直接删。
- 未拆分的普通规格仍是单份 `arch_design.md`；拉取请求就绪前晋升、归档或删除的生命周期不变。

**验收映射**：`VAL-LONG-RUNNING-001`、`002`。

#### 2.2.7 按类型写模型

**原始产品需求**：来源 Ben 反馈第 3 条前半。模型区分类型并写进标题；不同模型放一张表让人看不懂。

**用户可感知行为**：

- 取消混合各类模型的“模型总表”。每个模型一个标题，格式“名称（类型，改动）”，例如“`SeriesImagePosition`（数据库表，新增）”。每种类型只写对它有意义的字段：

  | 类型 | 必填 | 按需 |
  |---|---|---|
  | 领域实体 | 职责、唯一标识、生命周期 | 规则；状态三个以上时画状态图 |
  | 值对象 | 字段与取值约束、相等规则 | 规则 |
  | 枚举或状态 | 取值表：值、含义、何时进入 | 转换图 |
  | 数据库表 | 主键与唯一约束、字段改动表 | 索引、外键、迁移方式 |
  | 界面状态 | 状态取值、数据来源、谁能改它 | 转换图 |
  | 事件或消息 | 名称、载荷、发送方与接收方 | 重复投递怎么处理 |
  | 配置 | 键、谁读取、何时生效 | 默认值 |

- 接口的请求与响应结构、函数、方法和模块都不是模型，分别写在接口契约和分项的目录里。
- 字段改动表四列：字段、改动、含义、改成什么（修改写“原 → 新”）；不加“为什么”“现状”列，非显然的原因写取舍卡。
- 一个模型既是领域实体又直接对应一张表时，按主要用途选一种类型；没有独立代码载体的写“抽象概念”。位置规则不变：被两个以上分项或子设计使用的放共享模型。

**验收映射**：`VAL-MODEL-TYPE-001` ～ `004`。

#### 2.2.8 接口用签名和一句话说明

**原始产品需求**：来源 Ben 反馈第 3 条后半。“输入语义、输出语义”让人写得啰嗦，“输入 A、B，输出 C”就够了。

**用户可感知行为**：

- **进程内接口**：一行签名，一句“输入 A、B，返回 C”；调用方需要区分失败时再加一行“失败：D（什么时候）”。
- **HTTP 接口**：以一行“方法 路径（改动）”开头，一句话写谁调用、做什么；“鉴权”一行；写操作再加“重复请求”一行；然后是请求与成功响应示例和错误表（情况、HTTP 状态、错误码、调用方看到什么）。
- **消息或命令**：名称、谁发谁收、载荷示例、“重复投递”一行。
- 示例只注释非显而易见的字段（格式、单位、取值范围、什么时候为空）。兼容性变化仍要完整展示判断兼容所需的请求、响应和错误形态。

**验收映射**：`VAL-INTERFACE-BRIEF-001` ～ `003`。

#### 2.2.9 模板自身精简

**原始产品需求**：来源会话建议第 6 条后半和 `AGENTS.md` 编辑指引。模板砍掉大约一半，写作提示改成短规则，因为长段落会被模型模仿。

**用户可感知行为**：

- 用新规则替换旧规则，不在旧规则后追加例外；被取代的旧约定删除：固定层级编号、理由写进散文、参考依据表、分项“原始需求”小节、混合模型总表、六列结构变更表、以维度开头的观测与风险表、接口的“成功或输出语义”。
- 保留仍有效的硬约束：从真实代码出发、实体沿用仓库标识符、契约完整展示一次、退场清单逐路径闭包、有生命周期的模型写唯一标识和规则；`SKILL.md` 第 4、5 步的闭环检查同步改写。
- 模板文件不超过 16,400 字节（现有的 60%）；为达标删掉有效边界不算通过。

**验收映射**：`VAL-TEMPLATE-SIZE-001`、`002`。

### 2.3 规格类模板

规格可以看成产品需求文档的技术视角详细版：结构跟着产品走，再把边界、口径、失败语义和验收写精确。不是每个需求都有产品需求文档，没有时规格自己承担这些内容。

#### 2.3.1 要点页

**原始产品需求**：来源规格模板反馈和样本证据。拍板项不在文首，评审者要读到最后才知道哪些已定、哪些待定。

**用户可感知行为**：

- 文首一句话需求：面向谁、解决什么、做到什么结果；需要时跟几条“做法”要点。下面一行状态（2.1.3）；有产品需求文档时附链接与版本日期。
- 第 1 节固定是“要点”，依次包含：范围表（本期做、不在本期）；关键产品规则，编号 R1、R2……一句话一条，正文按编号引用；关键决定，编号列出决定、理由和谁确认；待确认表（问题、现状、需要谁确认），没有就写“无”。
- 正文不超过 1500 字，与架构设计的决策页同一上限（Ben 2026-10-26 确认）。

**验收映射**：`VAL-SPEC-SUMMARY-001` ～ `003`。

#### 2.3.2 需求详情按产品结构写

**原始产品需求**：来源样本证据和产品需求文档对比。每个叶子固定五个小节和六个字段，造成重复和空填；同一模板还产出了两种叶子写法。

**用户可感知行为**：

- 有产品需求文档时沿用它的页面或功能点结构和名称；没有时按用户可感知的子功能组织。模板只给一种叶子写法。
- 叶子开头“需求”一到三句加“来源”一行；行为用表写：场景表（场景、用户看到什么或系统怎么做、规则）；规则表（事项、规则，带“例：”）；异常表（场景、例子、结果）；数值表注明“当前配置，可调”。叶子末尾一行“验收：VAL 编号”。
- 不再有每个叶子的目标用户与场景、范围边界和兼容要求：用户在要点页说一次；容易误解的边界写一行“不包含”；兼容统一写在“已有功能兼容”一节（已有功能、本次的变化）。
- 平台类和技术类需求：用户是调用方或开发者时，场景表写调用方的动作和可观察结果，不硬套界面字段；“来源”区分“用户提出”和“Agent 建议、用户确认”。
- 规格不写技术方案（R4）：代码常量名、内部组件名、实施单元表和 Agent 分工分别属于架构设计和计划。

**验收映射**：`VAL-SPEC-DETAIL-001` ～ `004`。

#### 2.3.3 交互与文案表

**原始产品需求**：来源样本证据。交互表 6 列、文案表的最终文案在第 3 列，8 份样本无一使用，文案被塞进段落。

**用户可感知行为**：

- 交互用状态表：状态、用户看到什么、能做什么；动效、无障碍和适配只在有要求时写成要点。可用性启发式仍是写作时的自查，不进表。
- 文案表第一列是位置：位置、触发、文案（每种语言一列）、变量与兜底；格式与产品需求文档的文案表一致，便于对照。生产级用户表面仍必须写出本次新增或改变的全部文案。

**验收映射**：`VAL-SPEC-INTERACTION-001`、`002`。

#### 2.3.4 规格与产品需求文档的分工

**原始产品需求**：来源 Ben“规格像产品需求文档的技术视角详细版”和样本证据。带代码路径的调研发现排在需求前面；背景、来源在多处重复。

**用户可感知行为**：

- 有产品需求文档时，“为什么做”只写几句并链接它，不复述背景、竞品和视觉稿；规格补的是技术视角：精确口径、状态边界、失败语义、兼容和验收。实施依赖的契约（文案、规则、数值、异常结果）仍写进规格，因为飞书文档没有版本，仓库要保存实施时依据的内容（Ben 2026-10-26 确认）。
- 没有产品需求文档时（例如平台类、技术类需求或会话里直接提出的需求），“为什么做”用几句话写清问题、证据和替代方案，“来源”写用户原话；要点页和需求详情照常写。
- 来源对齐表、调研发现移到附录；没有来源结构时不填对齐表。附录另有术语表。

**验收映射**：`VAL-SPEC-SOURCE-001`、`002`。

#### 2.3.5 验收契约写法

**原始产品需求**：来源样本证据。“验收要求”和“通过标准”意思重复；同一句验证方式重复十几次；表头中英混写；三级验收映射难查。

**用户可感知行为**：

- 每个叶子一张表：编号、验收什么、通过标准、证据。“验收什么”一句话；通过标准写什么结果算通过，不复述要求；叶子里证据类别相同时，在叶子标题下写一次，不逐行重复。
- 只有需要驱动真实界面或跨层协作时，在文首列几条代表性验收路径；去掉逐叶子重复的覆盖总览（Ben 2026-10-26 确认）。
- 表头和正文只用中文；编号规则、单一含义和人工验收写明原因的要求不变。
- 拆成子规范时，子规范契约的行内写“承接父级 VAL-……”，伞形文档只保留父级到子规范的一张映射表。

**验收映射**：`VAL-VALIDATION-CONTRACT-001` ～ `003`。

#### 2.3.6 伞形文档与验证结果

**原始产品需求**：来源样本证据。伞形文档的子规范表有 7 列，其中三列是同一目录下的文件链接；待决归属在两个模板里用词不一致。

**用户可感知行为**：

- 子规范表五列：顺序、完整用户结果、目录（链接到子规范目录）、父级验收项、状态。
- 待决事项的归属统一写“架构、计划、实现”。
- 验证结果模板的记录规则不变，只统一用词和表头。

**验收映射**：`VAL-UMBRELLA-001`。

#### 2.3.7 规格类模板精简

**原始产品需求**：来源 `AGENTS.md` 编辑指引。

**用户可感知行为**：

- 用新规则替换旧规则；删除被取代的约定：固定五小节的示例与多层写法并存、用户可感知行为六字段、六列交互表、英文表头、验收三字段并列、来源在三处填写。
- `spec-design/SKILL.md` 里引用旧结构的地方同步改写；价值门禁、提问规则和生命周期不变。
- 四个规格类模板合计不超过现有的 23,418 字节。

**验收映射**：`VAL-SPEC-TEMPLATE-SIZE-001`、`002`。

### 2.4 技能调整

模板只管格子；写作原则和自检要写进技能正文，因为技能每次都会加载，写作的 Agent 动笔前就能看到。

#### 2.4.1 写作原则写进技能正文

**原始产品需求**：来源 Ben 反馈“核心的写作原则应该要纳入技能”。

**用户可感知行为**：

- `spec-design/SKILL.md` 和 `arch-design/SKILL.md` 各有一节“写作原则”，内容是 1.3 的 R1 至 R8，每条一句话。
- 模板只写各自的格式细节，开头写明“按技能的写作原则”，不再重复原则本身。
- 两份原则逐字相同，由仓库测试保证：改了其中一份而没改另一份，测试失败（Ben 2026-10-26 确认）。

**验收映射**：`VAL-SKILL-PRINCIPLES-001`、`002`。

#### 2.4.2 自检加可读性检查

**原始产品需求**：来源样本证据。现有自检只查需求、理由和影响是否闭环，不查文档好不好读。

**用户可感知行为**：

- `arch-design` 第 5 步在需求、理由、影响三项闭环之外，加“可读性闭环”：决策页不超过 1500 字；没有在两处定义的决定；没有只写“无”“不适用”的字段；核对类表格第一列是被核对的对象；修订已就地更新，没有追加段落。
