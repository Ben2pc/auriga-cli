# 已迁移技能安全清理 — Spec (已迁移技能安全清理 — 规范)

> 修复 Auriga 工作流插件升级过程中旧独立技能清理可能导致技能丢失、遮蔽或不可诊断的问题，并补齐当前子拉取请求与长期总规范之间的验收追踪。

## Why (为什么做)

PR #177 将 `systematic-debugging` 内化到 `auriga-workflow`，同时新增旧独立技能清理。合并后的正式评审发现，当前迁移对历史真实软链接布局、旧官方来源和市场更新失败场景的假设不成立，可能删除仍被另一运行时依赖的实体目录，或在插件仍不包含新技能时删除唯一可用副本。

同一评审还发现，长期总规范要求的父子验收映射没有落实到模板和首个子规范，导致“实现完成”“证据待补”和全局验收覆盖之间无法无歧义追踪。本次修复需要同时恢复安装安全和规范可信度。

## Findings (调研发现)

- PR #177 合并前的真实仓库布局以 `.agents/skills/<name>` 为实体目录，`.claude/skills/<name>` 是指向它的兼容软链接；`tests/plugins.test.ts` 当前把两者模拟成互不相关的实体目录。
- `src/plugins.ts` 当前按单个字符串判断历史来源，但 `session-compound` 与 `test-designer` 曾由 `Ben2pc/g-claude-code-plugins` 发布，后来才迁移到 `Ben2pc/auriga-cli`。
- Claude Code 市场刷新失败后，当前安装流程仍会尝试从旧缓存安装或更新插件，并立即执行破坏性迁移。
- 普通命令行安装没有迁移日志回调，来源不匹配、锁文件损坏和保守保留旧副本等状态不会对用户可见。
- 当前长期总览、总览模板和已归档子规范没有明确记录父级验收项到子级验收项的映射。
- 当前仓库不存在 `docs/rules/spec/` 与 `docs/rules/test/`，没有额外的项目专属规范或测试规则。

## What (做什么)

### 1. 保证跨运行时迁移安全

只迁移一个运行时时，未迁移运行时仍依赖的独立技能必须保持可用；软链接不能被留下为断链，断链也不能被当作有效技能副本或有效锁记录。

### 2. 识别完整的受管历史来源

迁移应识别每项技能所有已知的 Auriga 官方历史来源，同时继续保留来源不属于 Auriga 的同名自定义技能。来源不明确或锁文件不可读时采用保守保留，并向用户说明原因。

### 3. 仅在替代技能可用时执行破坏性清理

旧独立技能只能在目标运行时已经获得包含同名技能的 `auriga-workflow` 插件后删除。市场刷新失败、插件版本或内容无法确认、迁移过程部分失败时，不得把仍可用的旧技能静默删除。

### 4. 让安装结果和迁移结果可区分

插件安装与旧技能迁移分别报告结果。迁移失败不能伪装成插件未安装，也不能成功退出却隐藏仍会遮蔽插件的旧副本。项目级与用户级清理边界必须与目标运行时实际安装边界一致。

### 5. 恢复长期规范的父子可追踪性

长期总览和权威模板必须记录父级验收项由哪个子规范覆盖、哪些仍待补。当前 `systematic-debugging` 子项需要明确区分实现状态、迁移状态和目标模型评测状态，不再用“已完成”覆盖尚未执行的评测。

### 6. 用真实安装路径验证发布结果

预设安装后，Claude Code 与 Codex 都应发现插件提供的 `systematic-debugging`，且受管旧独立副本和锁记录不再遮蔽它。迁移回归测试必须使用历史真实目录与软链接拓扑。

## Out of scope (本次不做)

- 不执行 GPT 5.6 sol 或 Fable 5 的目标模型评测。
- 不根据尚未执行的模型评测继续修改 `systematic-debugging` 正文。
- 不清理来源无法证明属于 Auriga 的同名自定义技能。
- 不把长期规范的人工批准改造成新的 Ready 自动门禁。
- 不重构与本次迁移安全无关的插件安装架构。
