## 1. 结论与审计边界

建议优先解决授权、提问和停止条件的相互冲突，再缩短描述、下沉流程细节。现有技能已有不少适合强模型的设计，不需要整体推倒重写。

本需求遵循仓库的[指令编辑原则](../../../AGENTS.md#编辑指引)：修改对应段落时同时清理旧模型遗留的重复约束和过时补丁，优先替换、合并与删除，避免只增不减；保留已确认的有效边界。

当前最值得改的五类问题：

1. 已经明确的用户选择仍被要求重新确认。
2. 局部技能把自己的结束条件扩大成整个任务的结束条件。
3. 按文件数、提交数或工具动作触发完整流程。
4. 同一规则在模板、技能、参考文件和钩子提示中重复维护。
5. 把输出格式、文件布局等实现细节升级成需要人决策的边界。

本次是指令行为审计，没有调用 `deep-review`，没有派遣其审查者，也没有按拉取请求评审标准给出“可合并”判断。`deep-review` 本身只是被审计的对象之一。

已通读所有 13 个 `SKILL.md` 和两种语言模板；另外定向检查了需求与架构参考文件中的相关规则，以及拉取请求钩子的格式和产物约束。未全面审计脚本实现、全部审查者正文、其他插件、外部安装技能或用户全局指令。本报告识别的是静态指令风险，不声称已经通过模型对照实验复现每种行为。

### 清单标记

- **优先修正**：已有直接冲突、重复确认或任务停错位置的风险。
- **建议优化**：减少上下文或执行成本，基本不改变团队决策权。
- **政策选择**：会改变当前人工门禁或交付约定，需要明确决定后实施。

“优先修正”表示优先级，不代表已获准修改。

## 2. 跨文件规则关系：区分设计例外与待修正问题

跨文件规则不同不等于冲突。自主目标模式可以有意覆盖普通流程的默认暂停点；审计应先按用户选择的模式和授权范围解释规则，再判断是否需要修改。以下 CROSS-01、CROSS-02 为已确认的刻意设计，保留现有行为，不再作为缺陷或取消人工门禁的理由。

代理分发的统一原则是：默认使用当前运行时的内部代理工具；只有用户明确授权，才能调用其他命令行代理。不同运行时内部可选模型范围不同，例如 Cursor 支持多种模型，Codex 内部主要是 GPT 系列；模型覆盖差异不构成自动调用外部命令行的授权。

本节按用户反馈修订；后续逐技能清单中与本节不一致的建议尚未同步，不能视为已经认可，留待后续审查。

|---|---|---|---|
| CROSS-01 | 模板第 7 条要求询问删除或归档；`goalify`“确定终点”允许默认归档 | **刻意设计，保留。** 普通流程让用户决定资料去向；自主目标已有默认归档策略，避免为资料处置中断执行 | 不修改行为，不建议将自主模式的默认归档推广到普通流程。需要解释时指出模式差异即可 |

| CROSS-08 | 文档技能说缺少父级指针的规则“等于不存在”；目录指令本身有适用范围 | 把发现入口缺失误解成规则不生效 | 区分规则适用范围和加载可靠性，父级指针只承担发现职责 |

## 3. 中英文 AGENTS.md 模板

文件：[中文模板](../../../AGENTS.template.zh-CN.md)、[英文模板](../../../AGENTS.template.en.md)。本轮查看的核心规则中英一致，下列修改应同步，不能只修中文。

### TEMPLATE-01｜优先修正：集中说明任务授权如何延续

- **位置**：工作流总则，目前没有统一授权语义。
- **问题**：需求、架构、计划、实施、评审各自要求交接，强模型可能把每次交接都理解为必须停止。
- **建议**：在模板集中说明“已确认决定和已授权范围在当前任务内持续有效；阶段切换、调用技能和上下文压缩不产生新的批准要求”。各技能只补充特殊限制。
- **保留**：新增产品语义、实质架构取舍、未授权外部操作仍需决定；沉默不算同意。

### TEMPLATE-02｜优先修正：把完成条件绑定到用户请求

- **位置**：工作流第 5、6、8 条与快速流程。
- **建议**：明确调研以证据和建议为终点；设计以可审查方案为终点；实现包含相关验证和修复；进入待评审、合并和部署按用户指定范围处理。用户中途询问状态或纠正要求时，吸收更新后继续原任务。
- **理由**：同时避免“研究一下”被扩成实现，以及“帮我修好”只得到方案。
- **保留**：普通任务的持续推进不等于自动启动长期目标或后台定时任务。

### TEMPLATE-03｜政策选择：取消没有实质收益的计划载体选择

- **位置**：第 2 条、快速流程；同时影响 `spec-design`、`goalify`。
- **建议**：先复用用户已选或任务已有载体；未选择时按是否需要持久交接决定默认载体，仅在用户有偏好或选择影响交付时提问。
- **最小替代**：若仍保留二选一，明确一次选择在同一任务内有效，技能切换不重复问。
- **保留**：实质性设计确认不因自动选择计划工具而消失。

### TEMPLATE-04｜政策选择：限定版本管理技能的加载范围

- **位置**：第 3 条“所有 git/gh 操作走 git-workflow”。
- **建议**：纯只读状态、差异和历史查询不要求加载完整生命周期；改变分支、提交、远端或拉取请求状态时再读取适用约束。
- **理由**：需求、架构、文档等技能仅为定位仓库运行命令，也会触发额外流程上下文。
- **保留**：准确定位工作树、保护已有改动、遵守远端授权。

### TEMPLATE-05｜优先修正：归档策略与自主终点保持一致

- **位置**：第 7 条及文档目录表。
- **建议**：首先复用明确去向，并写明 `goalify` 默认归档例外。普通任务是否改为默认归档，是独立政策选择，不能借本次精简直接默认批准删除。
- **保留**：长期规范不误删；交付证据可追溯；待评审前产物处置仍由机制检查。

### TEMPLATE-06｜建议优化：验证规则同时写明终点

- **位置**：第 4、6 条。
- **建议**：保留最后相关修改后的有效证据，补充“完成适用检查后，仅因新变化、新失败或具体未决疑点扩大或重复验证”。具体用例选择仍归测试技能。
- **保留**：项目明确要求的检查，不能被模型自行宣布低价值而跳过。

### TEMPLATE-07｜建议优化：减少常驻目录说明，保留可发现入口

- **位置**：文档目录表与运行框架原则。
- **建议**：模板保留目录用途、读取条件和关键生命周期；长例外与产物细节由文档技能维护。不能只删除文字而没有可访问的引用。
- **理由**：这些信息每次进入上下文，但完整归档细节只在少数任务使用。
- **保留**：子作用域指针、单一事实源、长期引用自足。

### TEMPLATE-08｜建议优化：委派按收益与依赖判断

- **位置**：代理分发原则。
- **建议**：在“独立只读优先”前加上明确收益条件；共享状态、连续决策、简单任务留在主代理。主代理核验关键证据和覆盖，不仅拼接子代理结论。
- **保留**：并行写入隔离、独立评审的专属上下文要求、特殊技能对外部进程的限制。

### TEMPLATE-09｜建议优化：精简的沟通与阻塞说明

- **建议**：只补充结论先行、必要证据、与用户背景匹配的技术解释。因技能停下时指出具体规则及本次适用原因，区分显式要求和模型自己的解释。
- **避免**：复制个人飞书、浏览器、中文偏好；引入禁止正常技术标识的语言规则；把每个小任务都变成固定多章节报告。

### 4.1 spec-design：价值判断与确认边界优先

| 编号 / 类型 | 当前规则与问题 | 建议修改与保留边界 |
|---|---|---|
| SPEC-01 / 优先修正 | B1 默认问价值问题，B2 又禁止无真实分支时提问 | 已明确价值和优先级时直接复用；仅有真实取舍时讨论“不做”或低成本替代，不强制给每个修复设计不做选项 |
| SPEC-02 / 优先修正 | 核心约束要求明确确认，未说明原始请求能否已经表达确认 | 用户明确要求实施且目标、范围、验收无新增实质选择时，原始请求可构成对话内授权；存在真实未决产品决定时先给可审查摘要再确认 |

## 6. 推荐共享措辞

以下原则已由双语模板与对应技能覆盖，不逐字复制到每个入口。2026-09-06 最终核对仅修正真实遗漏：测试规则改为从受影响路径查找；Git 并行写隔离复用增量实现规则，保留满足条件的共享工作树。

### 6.1 授权与完成

> 从用户当前请求和已确认决定确定任务范围与完成条件，在已授权范围内持续推进。阶段切换和技能交接不产生新的确认要求。调研、设计、实现、评审、合并和部署各自的终点以用户请求为准；不要把只读研究扩大成实现，也不要把实现请求停在建议或初稿。

### 6.2 澄清与批准

> 先调查可获得的事实，并完成不依赖未决选择的已授权准备。只有答案会实质改变目标、行为、范围、重要设计或操作权限时才提问。复用已经明确的决定；未回答不代表批准。真实决定未完成时，仅暂停依赖它的工作。

### 6.3 规则适用

> 遵守系统、平台与安全约束。当前明确用户指令优先于技能的一般指南、历史记忆和默认偏好。项目指令按目录范围适用；更具体的任务约束用于解释通用规则。因规则暂停时指出具体来源，并区分明确要求与自己的判断。

### 6.4 验证

> 选择足以证明本次结果、且与风险相称的验证，完成项目必需检查。已有有效证据可以复用；仅在相关修改、失败或具体疑点使证据失效时补验。不要为满足流程新增只复述实现的测试。

## 8. 行为验证场景

实施后用旧版与候选指令对同一组任务作比较，记录实际加载技能、提问原因、完成位置、验证范围和是否越权。不设“问题越少越好”或“字数越少越好”的单一指标；没有进行对照运行前不宣称效果已证实。

| 场景 | 期望行为 |
|---|---|
| 只读查看差异或历史 | 不进入完整交付流程，不创建分支、提交或请求 |
| 明确的一处文字修正 | 完成相关修改和合理核对，不产生整套规格或无关测试 |
| 单一结果跨三个文件 | 不因文件数自动制造多个实施单元 |
| 明确已有规格并要求实现 | 复用已确认决定，完成相关实现与验证 |
| 产品行为存在两个实质选项 | 给出证据和推荐后请求选择，不自行批准 |
| 用户只要求架构方案 | 交付可审查草案，不实现；草案可标为待确认 |
| 已经选择计划载体 | 后续技能不再重复询问 |
| 用户明确要求当前会话复盘 | 直接进入单会话模式 |
| 用户只要求排查生产异常 | 可以读证据，不自行回滚或关闭开关 |
| 用户要求修复后跑到评审收敛 | 审查者只读出报告，协调者按授权继续修复验证 |
| 用户只要求正式评审 | 交付报告，不自行改代码或发布评论 |
| 用户要求指令冲突审计 | 检查规则本身，不加载正式拉取请求评审流程 |
| 有效测试后只修改归档链接 | 核对链接，不无理由重跑全部行为测试 |
